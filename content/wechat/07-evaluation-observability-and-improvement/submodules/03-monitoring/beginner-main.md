# 大话线上监控：系统没报错为何用户仍不满

周一上午，售后 Agent 的接口成功率是 99.9%，服务器也没有明显报错，客服群里却不断有人说“回答变慢”“总让我再说一遍”。排查后发现，政策搜索服务没有彻底挂掉，只是部分查询从 300 毫秒变成了 4 秒。Agent 等不到结果便走了降级路径，用通用话术追问用户，于是 HTTP 仍返回 200，业务体验却已经坏了。

普通服务监控关注可用性、延迟、流量和错误。Agent 在此基础上还要看任务是否办成、工具是否选对、是否反复循环、何时转人工、有没有触碰风险边界。否则仪表盘一片绿色，用户却在另一头冒烟。

## 一、HTTP 200 为什么不等于任务成功

对一个售后请求，接口成功只表示系统返回了响应。响应可能引用错政策，可能遗漏库存检查，也可能说“已创建申请”但订单系统里没有任何记录。技术成功与业务成功是两层概念。

监控应把最终业务状态带回来：换货草稿是否存在、工单是否被重开、用户是否再次进线、人工是否大幅修改、承诺与回执是否一致。没有即时标准答案时，可以先用代理指标，例如工具成功、正确升级、引用存在和用户重复求助，但要承认它们不是完整真值。

分母要稳定。任务成功率是成功任务除以全部进入 Agent 的任务，还是除以资料齐全且允许自动处理的任务？若路由规则改变，把难题都转人工，自动处理成功率可能上升，系统总体能力却没有变强。

## 二、Agent 线上监控要同时看四类信号

第一类是业务结果：完成率、工单重开、人工返工和最终业务状态。第二类是过程：工具错误、重试、循环、交接、拒答和护栏触发。第三类是资源：总延迟、各步骤耗时、`token`、并发和费用。第四类是风险：越权、错误写入、敏感数据、注入攻击和高风险动作的审批情况。

![Agent 线上监控的四类信号](./assets/monitoring-signals.png)

*图参考 [Google SRE 的四个黄金信号](https://sre.google/sre-book/monitoring-distributed-systems/)并结合 Agent 的任务、工具和风险信号改绘。普通服务的延迟、流量、错误与饱和仍要监控，但不能代替业务完成和安全结果。*

信号之间要能关联。搜索延迟上升后，Agent 重试次数和总 token 增加，最终转人工率也上升。单看其中一条只能看到症状的一角；把组件、版本、任务类型和 Trace 关联起来，才能判断影响链。

指标名称也要避免“成功”这类模糊词。`tool_http_200_rate`、`draft_created_rate`、`eligible_case_resolution_rate`各自含义不同。名字清楚、分母清楚，值班人员才能知道该不该叫醒谁。

## 三、指标、日志和 Trace 怎样接力

指标适合发现趋势：政策搜索 P95 延迟超过阈值，退款任务完成率下降。日志记录具体事件：某次查询触发超时，降级规则选择“请求用户补充”。Trace 串起一次任务的检索、模型和工具步骤，解释延迟如何传递到最终结果。

监控页面中的异常点最好能直接打开代表性 Trace，并按版本和任务筛选。若告警只写“延迟过高”，值班人员还要手工翻日志、猜请求和找用户，恢复时间会被浪费在拼图上。

日志与 Trace 不是越多越好。原始对话、订单和政策片段可能包含敏感数据，应保存必要摘要、标识和安全引用；指标标签也不能直接放用户 ID 或任意文本，否则会造成高基数，既昂贵又难聚合。

## 四、平均值怎样把局部故障藏起来

当天 90% 的简单问答仍在一秒内完成，10% 需要搜索政策的复杂工单变成八秒，平均延迟可能只从 1.1 秒升到 1.7 秒，看起来不算严重。对受影响用户而言，八秒就是每次都慢。

![平均值、分位数与业务切片](./assets/monitoring-slices.png)

因此要看 P50、P95、P99 等分位数，并按任务、地区、语言、客户、模型、工具和版本切片。P95 表示大约 95% 请求不超过该时长，它不会告诉你每个用户的体验，却能暴露尾部是否扩大。错误请求和成功请求的延迟也应分开，快速失败不应把平均值“优化”得更漂亮。

切片要控制数量。每个维度都与用户 ID 交叉会导致高基数和成本爆炸。先选择能影响处置的稳定维度，例如任务类型、风险等级、依赖服务和版本；具体用户问题通过 Trace 查询，而不是把身份塞进指标标签。

## 五、SLO 与错误预算怎样约束发布

服务水平指标 SLI 是可测量信号，例如“符合资格的换货任务在 10 秒内得到正确草稿或明确升级”。服务水平目标 SLO 是一段时间内希望达到的比例。错误预算则表示允许未达标的空间，用来平衡发布速度与可靠性。

![从 SLI 到 SLO 和错误预算](./assets/monitoring-slo.png)

Agent 的 SLO 不宜只写接口可用率。可以组合结果与时延，但定义要可执行；安全指标通常不应与普通可用性共享宽松预算。比如重复退款和越权访问即使极少，也需要单独严控。

当错误预算快速消耗时，团队应暂停高风险发布、优先修复或缩小自动化范围。若目标从不影响决策，它只是墙上的数字。反过来，SLO 也不能承诺模型永不出错，应基于业务风险、人工兜底和可承受代价设定。

## 六、告警应该让人知道下一步做什么

一个好告警包含症状、影响范围、开始时间、关联版本、关键依赖、代表性 Trace 和建议动作。搜索延迟告警应说明受影响的是需要政策检索的中文售后工单，当前完成率下降多少，是否刚有索引或路由发布。

![从异常信号到可执行告警](./assets/monitoring-alert.png)

阈值、变化率和异常检测可以组合。固定阈值适合明确上限，变化率能发现相对恶化，基线异常适合周期流量。但算法再聪明，也不应因为“某条曲线有点怪”就频繁叫人。告警要对应用户影响或即将需要人工处置的风险。

重复告警应聚合，低优先级问题可进入工单而不是电话。告警疲劳会让真正事故埋在噪声里。每次事故后检查：告警是否及时、是否可行动、是否指向错误团队，没用的告警要改或删。

## 七、降级、熔断和人工接管怎样选择

搜索变慢时，系统可以使用短期缓存、减少非必要检索、只返回待确认草稿，或将相关工单转人工。若写入工具状态不明，应熔断自动写入并保留现有状态。降级目标是缩小损害，不是悄悄给用户一个更差却装作完整的结果。

![异常后的降级与恢复路径](./assets/monitoring-degrade.png)

不同故障对应不同动作。模型服务拥塞可切换备用模型，但要确认能力和安全门槛；外部政策服务不可用时，不宜用模型记忆替代最新规则；费用异常可限制低价值的多轮尝试；高风险护栏异常应暂停动作，不以可用性为理由绕过。

恢复也要分阶段。依赖服务恢复后先用探测流量确认，再逐步解除熔断；检查积压任务是否仍有效，避免把过期写操作一次性重放。恢复完成后，补齐事故 Trace 和回归样本。

## 八、token 和成本异常为什么也是可靠性问题

某个版本可能成功率不变，却因为循环停止条件失效，把平均工具调用从 3 次拉到 11 次，费用和延迟一起上涨。若只看结果，几天后账单才会替监控发言。资源信号应按任务类型统计输入输出 token、模型调用、检索次数、重试和单任务成本。

成本告警也要结合价值。复杂投诉比查物流需要更多预算是合理的，统一阈值会误报。可以为不同任务设预算，超出后停止、降级或转人工。高 token 只是线索，还要查看 Trace 判断是上下文重复、工具失败、循环还是正常复杂度。

优化成本时不能只砍调用。减少必要核验可能让短期费用下降、返工和风险上升。应比较“每个成功任务的总成本”，包括模型、工具、人工和错误代价。

## 九、事故结束后还要验证什么

搜索服务恢复、曲线回落，不代表工作结束。团队要确认任务成功与人工接管回到正常范围，受影响工单是否补救，错误回复是否需要通知用户，积压状态是否一致。技术恢复和业务恢复可能相差很久。

然后整理故障时间线、触发原因、监控表现、降级效果和恢复步骤。把代表性样本加入离线回归，把有效操作写入处置手册，检查 SLO 和告警是否需要调整。若同类问题再次发生，系统应该更早发现、更小影响、更快恢复。

线上监控的目标不是让仪表盘永远绿色，而是尽早知道哪类用户正在受到什么影响，并有可信的缩小损害路径。Agent 会说话、会调用工具，也会把普通故障包装成一段流畅回复。监控必须穿过表面的 200，看到任务、过程、风险和代价。

## 十、用一次值班演练检查监控是否落地

可以人为制造三类低风险故障：让检索依赖持续变慢，让一个工具返回格式错误，再让某个租户的知识索引停留在旧版本。观察仪表盘多久出现异常、告警是否指出受影响任务和版本、值班人员能否直接跳到代表性 Trace。若告警只写“成功率下降”，还要手工翻日志猜范围，它只是把发现问题这一步自动化了一半。

演练还要检查处置。检索变慢时能否缩短链路或转人工，写入结果不明时能否停止重复提交，旧索引是否能按租户回退。恢复后要核对业务状态，而不是只看 CPU 和错误率回落。遗漏的信号、无效阈值和过期联系人都记录下来，下一轮修正。

监控配置本身也应像代码一样经过评审和版本管理。指标口径变化要说明分母，告警规则要有负责人、运行手册和最近演练时间。长时间从未触发的告警不一定代表系统完美，也可能代表规则已经失效。让监控接受测试，才不会在事故发生时第一次运行。

演练结束后保留三类时间：故障开始到被发现、被发现到完成止损、止损到业务完全恢复。它们分别检验信号、协作和补偿能力。若技术指标十分钟恢复，受影响退款两天后才核对完，就不能把恢复时间写成十分钟。Agent 的事故往往同时有技术尾巴和业务尾巴，两条都应关掉。

同一次事故还要记录“谁先知道”。若用户投诉早于系统告警，说明监控覆盖有缺口；若告警很早却没人处理，问题在路由或运行手册。把发现与行动分开衡量，才不会用一条很灵敏但无人负责的告警自我安慰。

每次重大版本发布前，重新核对这些监控是否携带新版本维度、任务类型和依赖信息。系统变了，旧面板未必仍能看见关键失败；监控也需要跟着产品一起发布。

值班手册与负责人名单也要同步更新。
