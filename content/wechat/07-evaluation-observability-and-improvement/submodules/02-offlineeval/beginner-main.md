# 大话离线评测：先在模拟考场里见真章

售后 Agent 换了新提示词，产品经理连续试了十条工单，觉得回复更简洁，工具调用也更果断。十条都不错，能不能上线？先别急。它可能只是恰好遇到熟悉题型，也可能为了“果断”少问了一个关键字段。离线评测要做的，不是给模型办一场热闹的演示，而是在固定题目和固定环境里，让新旧版本接受可重复比较。

团队准备了 300 个历史工单：退货、换货、价保、缺件、优惠券和物流异常。每条不仅有用户原话，还有订单状态、政策版本、允许工具、合格业务结果和禁止动作。Agent 跑完后，系统既检查最后答复，也检查它走过的步骤和真实工具结果。

## 一、先定义“办成了什么”，再挑指标

以换货工单为例，任务完成不是“生成一段礼貌回复”，而是资格判断正确、目标库存已核验、换货草稿创建成功，或在条件不满足时准确说明并转人工。若只评文字相似度，一个没有查库存却把标准话术背得很像的回答，可能拿到高分。

评测目标最好写成可观察条件。数值是否正确、工具是否调用、状态是否改变、引用是否存在，可以直接校验；解释是否完整、语气是否合适，可以给出明确评分标准。对资料不足案例，还要把“正确追问”或“正确拒答”列为合格，不逼 Agent 猜一个答案。

目标也要包含过程与风险。退款金额正确，但读取了不属于该用户的订单，不能算成功；回复无误，却把草稿直接提交，仍是越权。**Agent 的环境行为属于答案的一部分。**

## 二、评测集怎样覆盖真实任务

300 条题目不能只按“随便抽历史记录”得到。高频简单工单会占满样本，低频却严重的越权、重复退款和敏感信息泄露反而被稀释。更合适的结构是：一部分按真实流量采样，一部分覆盖边界和长尾，一部分来自线上故障，一部分由安全和领域专家设计。

![离线评测集的四类样本](./assets/offlineeval-dataset.png)

每条样本都要带必要元数据：任务类型、语言、风险等级、资料完整性、政策版本和期望行为。这样结果才能按切片分析。若不记录这些字段，只能得到一个总平均分，看不出优惠订单、英文请求或缺字段场景是否退化。

真实工单要去除无关个人信息，并由领域人员确认正确结果。历史客服回复不天然等于金标准，它可能也有错误，或者当时政策已经过期。把旧答案原封不动当标签，会让 Agent 学会复刻历史问题。

## 三、环境快照让新旧版本站在同一条起跑线

Agent 会读知识库、查订单、调用库存和创建草稿。若旧版运行时库存为零，新版运行时库存有货，最终差异不能归因于提示词。离线评测需要沙盒或可重放环境，把政策文档、订单数据、工具返回、系统时间和权限条件固定下来。

![Agent 离线评测的运行原理](./assets/offlineeval-harness.png)

*图依据 [OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)与 [GAIA](https://arxiv.org/abs/2311.12983)一类环境任务评测思路改绘。题目、环境、版本和评分器共同决定一次可重复评测。*

写操作在沙盒里执行，检查草稿内容和副作用，不碰真实客户。时间相关政策要固定“当前时间”，外部搜索结果最好保存快照或使用受控资料。随机性也要记录：模型和采样参数相同仍可能出现差异，可以对关键样本重复运行，报告通过率分布，而不是只跑一次决定命运。

环境并非越仿真越好。先保证关键业务条件和工具契约真实，再逐步加入网络抖动、超时和并发。若搭建一个昂贵的全量复制环境，却无法明确任务成功，仍只是更贵的演示台。

## 四、评分器要各管一类问题

确定性问题优先使用确定性评分：申请是否创建、金额是否等于订单实付、工具参数是否包含正确订单号、是否触发禁止动作。这些可以用规则、数据库状态或测试断言检查，没必要让另一个模型猜。

开放文本需要别的办法。可以检查关键事实与引用，再用带标准的模型评分完整性、相关性和表达；对重要样本做匿名人工复核。配对比较通常比让裁判凭空打 87 分更稳定：给出旧版与新版结果，随机顺序，要求按具体标准选更合格者并说明依据。

![规则、执行、模型与人工评分的分工](./assets/offlineeval-graders.png)

LLM 裁判会有位置偏好、冗长偏好、自我偏好和知识盲点。使用前要拿人工标注集校准，看不同错误类型上是否一致；定期抽查裁判分歧；输入中若含提示注入文字，还要防止被评测内容反过来操纵评分器。裁判是可扩展的测量工具，不是最后的真理机关。

## 五、为什么一个总分会掩盖问题

假设新版总体成功率从 78% 到 81%，看似进步。切片后却发现：普通退换货从 80% 到 86%，优惠叠加工单从 72% 降到 55%，高风险退款的错误写入多了两次。平均分把容易题的收益盖在严重退化上，发布结论应立即改变。

![总分与关键切片的差异](./assets/offlineeval-slices.png)

报告至少按任务、风险、语言、渠道、资料完整性和依赖工具拆分。每个切片要给样本数，五个样本的 100% 与五百个样本的 95% 不能并排当同等证据。新旧差异还要有不确定性说明；样本少时应扩大数据或人工复核，不要把随机波动写成稳定提升。

错误分类比总分更能指导修复。把失败区分为没检索到、证据用错、工具选错、参数错误、状态未写入、无依据完成声明和正确升级失败。不同类别对应不同负责人和改法。

## 六、数据污染与评测过拟合怎样出现

团队看到失败样本后不断调提示，直到 300 条全部通过，这并不代表真实能力提升。若每次都根据同一评测集改动，系统会逐渐“背题”；更糟的是把评测样本直接加入训练或提示示例后，仍用原分数宣称泛化能力。

应把数据分成开发集、回归集和保留测试集。开发集用于理解问题和快速迭代；回归集防止已知故障重现；保留集只在关键里程碑使用。线上新样本加入前记录来源、去重并检查是否与现有样本近似。公开基准用于了解通用能力，业务发布仍需自有任务集。

题目也会过期。政策变化、工具契约更新、产品流程调整后，旧标签可能不再正确。数据集要版本化，记录新增、修订和淘汰原因；比较长期趋势时说明使用的是哪一版考卷。

## 七、发布门槛不能只写“平均提升”

发布门槛分三类。第一类是硬门槛：越权、敏感信息泄露、错误退款、重复提交等不得出现或必须低于严格阈值。第二类是关键能力不退化：主要任务与高风险切片至少保持基线。第三类是优化目标：在前两类满足后，比较总体成功、时延、成本和人工接管。

![从离线评测到发布门槛](./assets/offlineeval-release-gate.png)

门槛还要考虑运行稳定性。关键样本重复五次，通过四次不能写成“已通过”；应报告 pass@1、稳定通过率或错误分布。若新版平均更好但波动明显变大，生产体验可能更难预测。

离线通过不是全量上线许可证。它表示候选版本获得进入影子或小流量灰度的资格。真实并发、最新数据、外部依赖和用户行为仍需线上验证，且任何安全指标恶化都应停止实验。

## 八、开放式任务如何验收

有些工单需要综合判断，没有唯一标准回复。此时可把完成标准拆成多项：关键事实是否覆盖、引用是否支撑主张、未知项是否明确、工具行为是否合规、下一步是否可执行。对自然语言质量使用成对比较和明确 rubric，不要求与参考答案逐字相似。

还可以让环境给结果。例如编码 Agent 是否修复问题，看测试与补丁；研究 Agent 是否找到正确数字，看来源和计算；客服 Agent 是否完成业务，看工单和订单状态。环境成功通常比“像参考答案”更接近真实目标。

人工评审应匿名和随机顺序，记录评审者分歧。若专家彼此都难以一致，说明标准还不够清楚，或任务本身存在多种合格答案。评测系统也要接受评测。

## 九、怎样从 300 条开始而不是等完美体系

先挑一个价值高、完成条件清楚的任务，收集几十条常见样本和真实失败。为每条补齐环境、合格结果、禁止动作和风险标签。能写规则的先写规则，开放部分再加模型评分和人工抽查。旧版作为基线，新版只改变少数明确变量。

随后按错误分布补样本，而不是盲目追求数量。每次线上事故考虑加入回归集，每次政策变化更新标签和快照。评测集会逐渐成为团队对“什么叫可靠”的共同合同，而不是某位同事电脑里的一张分数表。

离线评测的价值不在于提前算出生产成绩，而在于让明显错误不用等用户踩到，让版本比较有共同条件，让争论从“我觉得更好”变成“在哪些任务、以什么代价、改善了多少”。模拟考场不能代替真实世界，但没有考场就直接上路，未免太相信运气。

## 十、评测集也需要版本说明书

题目文件之外，还应保存这批样本从哪里来、适用哪些业务规则、使用哪份知识快照、评分器版本是什么、哪些人改过标签。政策更新后，旧答案可能从金标准变成错误答案；若没有变更记录，团队会误以为模型突然退化。评测报告因此要同时写候选版本和评测集版本，保留运行配置与原始轨迹。

定期做一次“考卷体检”：抽查标签，统计重复和近似样本，查看各切片比例，确认高风险事故仍被覆盖，并把过期题目移入档案。训练或调试频繁使用的样本不能继续承担独立验收职责，应另留一组保留测试。这样分数才表示对未知任务的判断，而不是对熟题的背诵程度。

评测运行失败也要单独统计。工具沙箱超时、测试数据缺失或评分器不可用，不应被悄悄记成模型答错，更不能从分母中删除。报告里区分系统失败、模型失败和无法判定，才能知道分数变化来自候选版本，还是考场本身出了故障。

每次发布后，把线上表现与离线预测对照：哪些切片判断准确，哪些在线上反转。差距长期存在，往往说明样本分布、环境模拟或评分标准需要更新。离线评测也要用生产事实校准，不能只在自己的分数体系里循环证明自己。

这份校准记录也应随评测集一起版本化。
