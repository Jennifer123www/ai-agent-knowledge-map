# 面试题：大语言模型从注意力到上线怎么答

![大语言模型面试题封面](./assets/llm-cover.png)

回答大语言模型题，最容易走向两个极端：一种只背“Transformer、注意力、预训练”，另一种只讲调用接口。比较完整的回答应从机制推到工程影响，再落到验证方法。下面八题刻意避开多模态、检索排序和微调细节，把范围留在语言模型推理本身。

## 问题 1：自注意力机制解决了什么问题？

### 原理

自注意力让序列中每个词元根据内容动态汇总其他位置的信息。查询与键计算相关性，归一化后的权重用于加权汇总值；多头机制让模型从不同关系角度建模。与固定局部窗口相比，它更容易捕捉远距离依赖，并支持训练阶段的并行计算。

![自注意力与上下文关系](./assets/llm-attention-context.png)

### 答题点

1. 先说明输入词元会变成带位置信息的向量；
2. 查询、键和值分别承担匹配和信息汇总，不要只背三个字母；
3. 多头关注不同关系，层叠后形成上下文化表示；
4. 标准注意力随序列变长计算和显存成本上升，长上下文需要优化。

### 记忆点

> 每个词都能按当前任务，决定该多看谁一眼。

### 追问

为什么还需要位置信息？仅靠注意力无法区分词元先后，相同集合的不同排列可能得到相似处理；位置编码或旋转位置表示为顺序和距离提供信号。

### 失分点

只说“注意力让模型关注重点”，没有查询、键、值、位置和复杂度。

## 问题 2：上下文窗口很长，模型为什么仍会漏掉关键信息？

### 原理

窗口容量只说明输入放得下，不保证模型对每个位置同等利用。长上下文中的噪声、重复、矛盾、位置偏差和任务指令竞争，都会降低关键信息的可见度；训练时见到的长度分布也影响模型对极长输入的泛化。

### 答题点

1. 先区分容量、有效利用率和最终答案准确率；
2. 对资料做检索、排序、去重和来源标记，减少无关内容；
3. 把任务、硬约束和关键证据放在清楚结构中，不依赖堆叠历史；
4. 用长文定位、跨段合成、冲突证据等专项样本测试。

### 记忆点

> 桌子够大，不代表每张纸都看得见。

### 追问

能否用摘要替代完整历史？可以降低长度，但摘要会丢细节。关键数字、权限、待办状态和引用应结构化保留，摘要只承担叙事压缩。

### 失分点

把所有问题归因于“超过窗口”，忽略窗口内的信息稀释与位置效应。

## 问题 3：温度、Top-k 和 Top-p 分别怎样影响输出？

### 原理

模型每一步产生词元概率分布。温度调整分布尖锐程度；Top-k 将候选限制在概率最高的固定数量；Top-p 选择累计概率达到阈值的动态候选集合。随后再从保留集合中采样。

![采样参数与输出多样性](./assets/llm-sampling.png)

### 答题点

1. 低温度通常更稳定，高温度通常更多样，但不等于事实更真或更假；
2. Top-k 控制候选数量，Top-p 根据分布形状调整候选范围；
3. 参数会相互作用，不能脱离具体服务实现机械套数值；
4. 抽取和工具调用偏稳定，创意生成可适度增加多样性，并通过评测定值。

### 记忆点

> 温度调平陡，Top-k 数名额，Top-p 看累计概率。

### 追问

温度为零是否完全确定？不一定。服务端实现、并行计算、模型版本和相同分数的处理仍可能造成差异，更不能保证答案正确。

### 失分点

说“温度越低越准确”，把随机性与事实性混为一谈。

## 问题 4：语言模型为什么会产生幻觉，怎样治理？

### 原理

训练目标鼓励生成符合语言分布的后续词元，并不直接验证每个事实。知识过期、证据缺失、问题错误前提、上下文冲突和工具异常，都可能让模型生成流畅但无依据的内容。

![大语言模型可靠性护栏](./assets/llm-reliability.png)

### 答题点

1. 按任务区分创意、一般事实、实时状态和高风险决策；
2. 一般事实通过检索和引用约束，实时状态通过权威工具获取；
3. 允许“不知道”、追问和停止，不强迫模型对所有输入给肯定答案；
4. 评测陈述与证据的一致性，并跟踪错误来自检索、拼装还是生成。

### 记忆点

> 不让模型凭空记真相，让它拿证据说话。

### 追问

检索增强能否消除幻觉？不能。检索可能漏掉、召回错误或被错误引用；生成模型也可能歪曲证据，因此还需要排序、引用核验和业务校验。

### 失分点

只答“优化 Prompt、降低温度”，没有事实来源、拒答、验证和责任边界。

## 问题 5：怎样提高结构化输出和工具参数的可靠性？

### 原理

结构化输出把自然语言生成约束到模式中，但模式只保证形状，不保证业务正确。可靠链路需要模型侧约束、程序侧解析、业务侧校验和执行结果回传。

### 答题点

1. 使用清晰字段名、类型、枚举、必填项和字段说明；
2. 优先使用模型服务提供的结构化输出或工具调用能力；
3. 执行前检查范围、资源归属、权限、幂等键和当前状态；
4. 失败时返回结构化错误，引导补参、改参、重试或人工处理。

### 记忆点

> Schema 保证长相，业务规则保证能不能做。

### 追问

参数通过 JSON Schema 就能直接执行吗？不能。合法金额可能超过额度，合法订单号可能属于其他用户，必须做授权与业务状态校验。

### 失分点

只说“要求模型输出 JSON”，不处理多余文本、缺字段、越权和重复执行。

## 问题 6：大语言模型推理时延主要来自哪里，怎样优化？

### 原理

推理通常分为处理输入的预填充阶段和逐词元生成的解码阶段。长输入增加预填充计算，长输出增加串行解码时间；模型规模、硬件、批处理、缓存和并发调度都会影响实际延迟。

![大语言模型的词元生成循环](./assets/llm-token-generation.png)

### 答题点

1. 分开监控首字延迟、每词元延迟和完整响应时间；
2. 清理无效上下文、限制不必要的输出长度，避免重复传输大前缀；
3. 对稳定前缀使用提示缓存，对离线任务使用批处理；
4. 根据质量门槛选择更小模型、量化版本或专用模型，并设置超时。

### 记忆点

> 输入长拖预填充，输出长拖解码。

### 追问

流式输出是否降低总时延？通常改善用户感知的首字等待，但不一定缩短完整生成时间；后端任务仍要等待完整结构时，收益有限。

### 失分点

把网络、检索和工具耗时都算成模型慢，或只说“加 GPU”。

## 问题 7：怎样在小模型和大模型之间做路由？

### 原理

路由目标是在满足质量和安全门槛的前提下降低成本与延迟。可以先用确定性规则识别模态、长度、领域和风险，再结合分类器、置信信号或历史评测选择模型；失败时按策略升级。

### 答题点

1. 定义适合小模型的稳定任务，如分类、改写和格式转换；
2. 对复杂推理、长上下文和高风险任务直接选择强模型；
3. 路由器自身也要评测，观察误路由率和升级率；
4. 记录选择原因与最终结果，防止成本下降掩盖质量退化。

### 记忆点

> 简单任务走快车，复杂任务别省错钱。

### 追问

让小模型先答、低置信再升级是否总能省钱？不一定。若置信不校准或大多数任务都会升级，就增加一次调用和时延；应对真实分布做成本模拟。

### 失分点

只按输入长度路由，忽略任务风险、模态、领域和失败代价。

## 问题 8：语言模型线上质量突然下降，排障顺序是什么？

### 原理

线上结果由输入、系统指令、上下文、模型版本、采样参数和工具结果共同决定。排障要保存可复现的请求快照，并先检查最近变更和外部依赖，再定位是普遍退化还是特定切片异常。

### 答题点

1. 对比模型、提示、参数、上下文模板和安全策略的发布记录；
2. 按任务、语言、输入长度和租户分组观察错误率；
3. 重放固定样本，比较原始响应、结构解析和后处理；
4. 若影响扩大，先回滚或降级，再用失败样本补回归集。

### 记忆点

> 先看变更，再看切片，最后重放证据。

### 追问

供应商模型名称没变，行为会变吗？托管模型可能更新底层版本或服务策略，因此仍需监控、固定可用版本，并用持续回归检测行为变化。

### 失分点

拿一条失败对话反复改提示，却没有版本、原始请求、分层指标和回滚动作。

## 问题 9：KV Cache 和提示缓存分别解决什么问题？

### 原理

KV Cache 保存一次生成过程中历史词元在注意力层的键和值，避免每生成一个新词元都重算全部前文。提示缓存则尝试在不同请求之间复用完全相同或可共享的前缀计算。前者是单次自回归解码的基础优化，后者是跨请求的服务优化。

### 答题点

1. KV Cache 用计算换显存，长度和并发越高，容量压力越大；
2. 提示缓存适合稳定系统指令、模板和公共上下文；
3. 缓存键要绑定模型与前缀，避免版本错误和用户数据串用；
4. 监控命中率、显存、首字延迟和淘汰，不能只看请求数。

### 记忆点

> KV Cache 省同一次续写，提示缓存省不同请求的共同开头。

### 追问

为什么长上下文会压低并发？每条序列的 KV Cache 占用增长，有限显存能同时容纳的请求变少，调度与排队也随之变化。

### 失分点

把两种缓存当成普通答案缓存，忽略计算状态、前缀一致性和隐私隔离。

## 问题 10：分词器为什么会影响质量、成本和上下文？

### 原理

分词器把文本拆成模型词元。不同语言、代码、数字和专有名词的切分效率不同，同样字符数可能产生不同词元数。词元数量影响上下文占用、计费和推理时延，切分方式也影响字符级与数字任务。

### 答题点

1. 容量和成本应按词元估算，不能只按字数；
2. 罕见词、连续数字和代码可能被拆得更碎；
3. 模型与分词器必须版本匹配，不能随意替换；
4. 精确计数、算术和格式校验应交给代码，不依赖词元直觉。

### 记忆点

> 模型吃的是词元，不是界面上看到的字数。

### 追问

为什么中文一万字不一定等于一万词元？常见词、单字、标点和编码方式会产生不同切分，需用对应模型的分词器实测。

### 失分点

把 token 简单翻译成“单词”，忽略中文、代码和数字的切分差异。

## 面试收束：把机制落回工程变量

回答这组题时，可以始终沿一条线展开：机制是什么，它改变了哪个工程变量，怎样用评测验证。自注意力连接上下文，也带来长序列成本；采样增加多样性，也增加输出波动；结构化输出约束形状，却不替代业务校验；缓存降低重复计算，也带来显存、失效和隔离问题。

若面试官继续追问模型内部细节，不必用一串名词挡住问题。先给准确直觉，再说明公式或实现的作用，最后回到时延、质量和故障。真正有项目感的答案，通常知道哪些结论由模型产生，哪些事实必须由外部系统确认。
