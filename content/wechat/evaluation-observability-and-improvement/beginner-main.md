# 大话智能体评测：它到底把事情办成了吗

一家电商把售后工单交给 Agent 辅助处理。新版上线后，后台显示“自动结单率”从 62% 升到 74%，团队正准备庆祝，客服却发现两件怪事：用户再次来问同一问题的比例上升了，人工把工单重新打开的次数也变多了。系统确实更爱点“完成”，但它是否真的解决了问题，答案没有报表看上去那么喜庆。

Agent 会检索政策、调用订单接口、判断下一步、生成回复，有时还会修改业务状态。评测它，不能只读最后一段话，也不能只看接口有没有返回 200。需要同时回答四个问题：结果对不对，过程是否合规，代价是否合理，出了错能否定位。链路追踪、离线评测、线上监控、版本发布和反馈实验，正是为这四个问题提供不同证据。

## 一、结单率上涨为什么仍不能证明系统变好

先看一个具体工单：用户说“鞋码不合适，吊牌还在，想换大一码”。Agent 查到退换政策后回复可以换货，并把工单标为完成。文字顺畅、政策也没错，但它没有检查目标尺码库存，更没有创建换货申请。若指标只看“回复已生成”和“工单已关闭”，这次会被记成成功；用户第二天重新进线，才暴露任务根本没有办完。

**指标必须贴着业务交付物，而不是贴着模型动作。**这类工单的完成条件至少包括：资格判断正确、库存已核验、申请草稿已创建或明确转人工、回复中的承诺与系统状态一致。模型说“已处理”只是一个文本事实，订单系统的申请编号才是业务事实。

还要把“无法自动完成但正确升级人工”算作一种合格结果。若证据不足或权限不够，安全停下比自信结单更可靠。任务成功率的分母也要写清：是所有进入系统的工单、具备完整资料的工单，还是允许自动处理的低风险工单。分母不清，同一个 74% 可以讲出三种故事。

## 二、结果、过程、风险和资源要分开看

一个可用的指标体系至少有四层。第一层是结果：问题是否解决、业务状态是否正确、关键事实是否有证据。第二层是过程：工具是否选对、参数是否正确、是否发生无效循环、该交接时有没有交接。第三层是风险：是否越权、是否泄露敏感信息、是否绕过审批、是否在证据不足时编造。第四层是资源：耗时、`token`、工具调用次数和费用。

![Agent 评测的四层指标](./assets/evaluation-metric-layers.png)

四层不能压成一个漂亮总分。假设版本 A 任务成功率高 2%，却把越权写入从万分之一推到千分之一；若简单加权，质量收益可能把严重风险“平均掉”。更稳妥的做法是把安全、合规和不可逆副作用设成硬门槛，再在合格版本中比较质量、时延和成本。

指标之间也可能拉扯。让 Agent 多查两个来源，引用质量也许提高，延迟和费用却会上升；为了压缩步骤限制工具次数，可能让复杂工单更早转人工。评测不是找一个永远最大的数字，而是把这些取舍摆到同一张证据桌上。

## 三、链路追踪把一次任务还原出来

用户投诉错误时，只保存最终回复远远不够。一次任务需要一个统一的 `Trace ID`，模型调用、政策检索、库存查询、换货草稿和人工交接分别记录为 `Span`。每个 Span 有开始和结束时间、父子关系、状态、版本与必要的输入输出摘要。这样才能从“回复错误”向前追：是否检索到旧政策，是否工具参数用了错误订单号，还是库存接口成功但结果没有进入下一步。

![从一次工单到完整证据闭环](./assets/evaluation-loop.png)

*图依据 [OpenTelemetry 可观测性概念](https://opentelemetry.io/docs/concepts/observability-primer/)和 [OpenAI Agents SDK Tracing](https://openai.github.io/openai-agents-python/tracing/)改绘。Trace 串起单次过程，评测和监控再把多次过程汇总为质量证据。*

追踪不是“把全部对话永久存下来”。提示词、检索片段和工具结果可能包含地址、电话和订单信息，应按用途选择字段，做脱敏、访问控制、采样与保留期管理。能复现问题和无限复制原文不是一回事。真正有价值的是关联关系、版本、决定下一步的事实和外部系统回执。

## 四、离线评测先建立可重复的比较

团队从历史工单中抽出 300 条，去除不必要的个人信息，补充期望结果、允许使用的工具、关键政策版本和禁止动作。旧版与新版在同一套沙盒数据上运行，才能比较谁真正改善。若新版连的是最新库存，旧版连的是过期快照，成绩差异就混入了环境变化。

评分也应分层。申请是否创建、金额是否一致、工具参数是否合规，可以用规则或执行结果确定；回复是否完整、解释是否清楚，可以用带评分标准的模型评审，并由人工样本校准；高风险案例最好由领域人员复核。模型裁判适合扩大覆盖，不适合宣布自己永远公正。

![从失败类型回到具体环节](./assets/evaluation-failure-attribution.png)

离线集要包含常见问题、资料缺失、政策冲突、接口超时、恶意输入和低频高风险任务。只收集“标准问法”会把考场布置得比生产环境整齐得多。还要按任务类型、语言、渠道和风险等级分开报告，否则整体平均分上升，可能掩盖退款类工单明显退化。

## 五、线上监控负责看真实世界有没有变

离线评测固定了题目与环境，线上监控面对不断变化的用户、数据和依赖。政策服务可能换版本，搜索接口可能变慢，节日促销会带来新问法，某个地区的库存字段也可能突然为空。监控要持续观察任务成功、重新进线、人工接管、工具错误、安全拦截、P95 延迟、`token` 和费用。

平均值尤其会骗人。若 95% 的简单工单很快，5% 的退款工单卡在外部接口，平均延迟仍可能好看。按任务、语言、客户、工具版本和风险级别切片，才能看见局部故障。指标异常后再跳到关联 Trace，监控回答“哪里不正常”，追踪回答“这一次为什么不正常”。

告警要带可执行动作。库存查询失败率上升时，可以暂停自动承诺、改为只给待确认答复，并把相关工单送人工；写入接口状态不明时，应停止重试而不是继续赌。没有降级和责任人的告警，只是更响亮的报错。

## 六、版本与发布管理让改动可以归因

Agent 的版本不只是模型名称。提示词、模型参数、检索索引、文档版本、工具契约、工作流、规则和评测集都会改变行为。每次运行若不记录这些版本，新旧结果就无法复现，出问题时也不知道应该回退哪一部分。

候选版本先过离线回归和安全门槛，再进入影子流量或小范围灰度。影子流量用真实请求运行候选版本但不影响用户，适合观察行为和成本；灰度让少量真实用户使用新版本，观察业务结果。若要比较哪种方案造成了提升，需要尽量固定其他变量，并采用合理的随机分流或配对设计。

![发布前需要通过的证据闸门](./assets/evaluation-evidence-gate.png)

发布还要预设停止条件：越权、错误写入、严重投诉等风险指标一旦触发，应立即停止；任务成功、时延和成本达到什么范围才扩大流量，也应提前写清。上线后临时挑一个有利指标，不是实验，是给结果找理由。

## 七、用户反馈要先变成可诊断信号

点赞、差评、重新提问、人工改稿和最终退款是否成功，含义并不相同。用户可能喜欢一段礼貌但错误的答复，也可能给正确答复差评，只因为政策本身不合心意。反馈必须关联原任务、Trace、版本和业务结果，才能判断问题出在知识、推理、工具、流程还是产品界面。

客服反复把“退款 129 元”改成“退回实付 109 元”时，最有价值的不是差评数量，而是修改前后字段、订单优惠构成、模型看到的证据以及最终业务回执。复核后可把这类案例加入离线集，建立金额口径检查，再验证修复是否同时改善普通订单和优惠订单。

反馈也要排序。高频措辞问题可以排在低频越权之后；一个偶发的数据泄露风险，优先级通常高于上千条“回答有点啰嗦”。持续优化不是谁声音大就先改谁，而是结合影响范围、严重度、可复现性和修复成本安排。

## 八、五个子模块怎样真正闭环

完整闭环从线上事件开始：监控发现退款工单重新进线率上升，Trace 定位到新版检索选中了旧政策，反馈记录补充了客服的正确改稿。团队把代表性失败加入离线评测，修复索引过滤后运行回归，再通过影子和灰度发布验证。指标恢复且没有触发安全门槛，才逐步扩大流量。

![新旧版本必须与简单基线比较](./assets/evaluation-baseline.png)

这五部分缺一块都会变形。只有 Trace，会得到许多可以翻看的故事，却不知道整体是否改善；只有离线分数，会看不到真实流量的新问题；只有监控，会发现数字变了却无法定位；只有反馈，会被情绪和样本偏差牵着走；只有发布平台，没有可信评测与停止条件，只是更快地把不确定性推给用户。

还要保留简单基线。新版 Agent 应与旧版、单次模型调用、规则流程或人工方案比较。若多轮调用只提升一点点成功率，却让延迟和费用翻倍，业务未必值得买单。评测的职责不仅是证明新方案有效，也包括证明复杂度确有必要。

## 九、从最小证据链开始建设

第一步，挑一个有明确业务结果的任务，例如“创建换货草稿”，写出成功、正确拒绝和人工升级的条件。第二步，为一次运行建立 Trace，至少关联模型、检索、工具、状态与版本。第三步，从历史正常样本和真实故障各选一批，形成小而可信的离线集。第四步，在线上建立任务成功、错误、延迟、成本和风险五类基本监控。

随后再增加灰度、A/B、自动评分和反馈回流。顺序很重要：没有任务定义，采集再多数据也不知道什么叫好；没有版本和轨迹，指标变化无法归因；没有离线门槛，线上实验会把本可提前发现的问题交给用户。

Agent 评测最终要回答的不是“这段话像不像高手写的”，而是：它有没有完成承诺的任务，关键步骤是否有证据，风险是否受控，成本是否值得，失败后能不能找到原因并稳定修复。把这五个问题持续答清楚，才算真正进入生产。

每次评审都可以固定问一句：“如果明天这个指标变差，我们能否指出受影响的任务、对应版本、代表性轨迹和处置办法？”答不上来，就说明证据链仍有断点。先补断点，再扩展更复杂的评分和自动化，建设次序会稳得多。
