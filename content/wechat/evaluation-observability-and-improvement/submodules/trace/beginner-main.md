# 大话链路追踪：一句错答从哪里开始

用户买了一台咖啡机，签收第十天申请退货。售后 Agent 回复“已超过七天无理由退货期，无法办理”，客服却发现该商品页面承诺十五天可退。最终回复只有一句话，错得很干脆；真正麻烦的是，团队不知道它为什么错。是检索没找到商品专属政策，重排序把通用条款放在前面，模型忽略了日期，还是订单工具返回了错误品类？

链路追踪要解决的就是这种“结果能看见，过程藏在系统里”的问题。Trace 表示一次端到端任务，Span 表示其中一段明确操作。把模型、检索、工具、状态和交接串在同一条时间线上，错误才不再是一团雾。

## 一、只保存最终答案为什么查不出问题

最终回复可以告诉我们“说错了什么”，却不能告诉我们错误从哪一步进入。若 Agent 根本没检索商品政策，应该修路由；若检索到了但排在上下文末尾，应该查排序和上下文构造；若证据正确而模型仍引用通用条款，才轮到提示或模型行为。三个故障表面相同，修法完全不同。

普通应用常用日志记录“某时发生某事”，但 Agent 一次任务会跨模型服务、向量检索、订单 API、规则服务和工作流状态。各组件日志散在不同系统里，时间格式、请求标识和字段名称还可能不同。没有统一关联标识，排查者只能凭时间猜哪几行属于同一位用户。

链路追踪先为用户任务生成 `Trace ID`。后续每次检索、模型调用和工具执行都携带这个标识，并创建自己的 `Span ID`。即使调用跨进程、跨队列或交给另一个 Agent，也能沿父子关系拼回一棵执行树。

## 二、Trace 与 Span 到底是什么

Trace 可以理解成一张任务总票据：从用户提出退货请求开始，到系统给出结果、暂停或转人工结束。Span 是票据上的一项明细，例如“查询订单”“检索政策”“调用模型”“检查资格”“生成回复”。每项都有开始时间、结束时间、状态和必要属性。

![一次售后任务的 Trace 与 Span 树](./assets/trace-tree.png)

*图依据 [OpenTelemetry Trace 语义约定](https://opentelemetry.io/docs/specs/semconv/general/trace/)和 [OpenAI Agents SDK Tracing](https://openai.github.io/openai-agents-python/tracing/)改绘。父子关系表示调用依赖，不表示每个组件都必须来自同一框架。*

父 Span 通常代表更大的操作，子 Span 代表其中的调用。退款资格判断可以包含订单查询、政策检索和规则核验三个子 Span。若两个资料源并行检索，它们在时间线上可以重叠；若政策检索结束后才开始模型生成，则能看出真实依赖。Span 不是随手画的层级，而是系统实际发生的操作边界。

结束状态也要有语义。成功表示该操作按契约完成，错误应带稳定错误类型，取消与超时最好分开。一个 HTTP 200 的工具调用仍可能是业务失败，例如返回“订单不存在”；技术状态与业务状态不能混成一个字段。

## 三、父子关系和时间线如何还原过程

这张错误工单的 Trace 显示：订单查询得到商品编号 `C-204`，政策检索同时查了“通用退货规则”和“商品活动承诺”，重排序只把通用条款送入模型，模型因此按七天规则拒绝。根因不在模型凭空发明，而在候选过滤遗漏了活动政策。

时间线还能发现性能问题。若政策检索只用 80 毫秒，订单工具却等待 4 秒并重试两次，用户感受到的慢主要来自外部依赖。若模型生成前有 3 秒空白，则要检查队列、限流或状态锁。仅看总耗时无法区分“哪段慢”和“为什么等”。

并发会让树更复杂。两个并行分支可能共享同一父 Span，交接给另一个服务后还会跨进程。传播机制要把 Trace 上下文放进 HTTP 头、消息属性或任务载荷；若队列消费端重新生成无关 ID，链路会在最需要排查的地方断掉。

## 四、每个 Span 应该留下哪些字段

字段要服务于问题，而不是越多越安心。通用字段包括操作名称、开始结束时间、状态、父子标识、服务与环境。模型 Span 记录模型和提示模板版本、输入输出 `token`、停止原因与响应标识；检索 Span 记录查询摘要、索引版本、候选标识和排序结果；工具 Span 记录工具版本、参数摘要、错误码与业务回执；状态 Span 记录前后状态和转移理由。

![不同 Span 应保留的关键字段](./assets/trace-span-fields.png)

版本字段尤其关键。同一句提示配不同模型、同一个查询配不同索引、同一个工具名配不同契约，行为都可能变化。只记录“调用了 search_tool”不足以复现；至少要知道工具契约版本和依赖数据版本。

输入输出不必全部原样保存。订单号可散列或只保留安全引用，政策片段可以记录文档标识、版本和段落定位，敏感正文放在受控存储。对排查有用的是“看了哪份证据、作了什么判断”，不是让每个观测平台都复制用户隐私。

## 五、怎样沿轨迹定位根因

排查从业务失败开始，不是从红色错误图标开始。先确认合格结果应该是什么，再找到实际输出与完成状态；随后沿父子 Span 向上检查决定结果的证据、工具回执和状态转移。技术上最慢或最早报错的节点，不一定是业务根因。

![从用户投诉到可验证根因](./assets/trace-diagnosis.png)

在咖啡机案例中，模型 Span 正常结束，不能据此宣布模型没问题。它的输入只包含通用政策，继续查看检索 Span 才发现活动条款被过滤。再与同版本成功工单比较，确认这些工单的商品标签正确触发了活动索引。于是修复假设变成“活动商品标签缺失导致检索范围错误”，可以用一组带活动承诺的工单回归验证。

根因结论要能被反驳。若只是说“模型偶尔不稳定”，既没有定位字段，也没有复现实验。好的归因会指出哪个版本、哪类输入、哪一条状态或哪项依赖导致失败，并说明修改后哪些样本应改善、哪些不受影响。

## 六、日志、指标和 Trace 各自擅长什么

指标回答“整体发生了多少”：失败率是否升高，P95 延迟是否恶化，某工具调用量是否异常。日志回答“某个时刻记录了什么”：错误码、策略拒绝、状态变更。Trace 回答“一次请求怎样穿过系统”：哪些操作互相依赖，时间花在哪里，哪份证据进入了哪次模型调用。

三者最好能相互跳转。监控发现退款失败率上升，按标签筛到政策检索组件；从异常点打开代表性 Trace；在对应 Span 中查看结构化日志与业务回执。若三套系统各用一套标识，排查仍要靠复制粘贴和猜时间。

结构化很重要。日志即使写成 JSON，字段今天叫 `orderId`、明天叫 `order_no`，下游仍难可靠分析。稳定字段、清楚类型和统一语义，比把自然语言报错塞进大字段更有用。

## 七、为什么不能全量保存所有内容

全量追踪听起来最利于排错，却有三笔账。第一笔是成本：长提示、文档片段和工具结果会让存储与检索迅速膨胀。第二笔是安全：日志平台可能因此持有地址、身份证号、合同和密钥。第三笔是噪声：大量原文会淹没真正决定结果的字段。

![追踪采样的分层策略](./assets/trace-sampling.png)

可以按风险与用途分层。错误任务、高风险写操作和新版本灰度保留更完整轨迹；稳定低风险流量按比例采样；指标始终聚合；特定事件发生后采用尾部采样，保留慢请求或失败链路。采样规则要记录版本，否则今天与上周的 Trace 数量不能直接比较。

采样也会偏。只保留报错请求，可能看不到“返回成功但答案错误”的隐性失败；只按延迟采样，会错过快速越权。业务反馈、护栏事件和随机样本应共同进入保留策略。

## 八、脱敏、访问控制和保留期怎样配合

脱敏不是简单把所有数字替换成星号。应先做数据分类：哪些字段无需采集，哪些可以摘要或散列，哪些原文只允许在受控系统查看。工具参数中可能混有密码或访问令牌，这类值应在进入追踪前删除，而不是寄希望于展示端遮住。

![追踪数据的隐私治理边界](./assets/trace-privacy.png)

访问权限按职责分开。工程师可能需要看错误类型和版本，客服主管可以看业务过程，只有获授权人员能查看敏感原文。导出和查看高敏 Trace 本身也要审计。保留期根据排障、合规和申诉需求设置，到期删除时还要处理派生索引与缓存。

租户隔离不能依赖前端过滤。Trace 查询层应带真实身份和租户条件，避免一个客户的轨迹出现在另一个客户的调试页面。可观测性是生产系统的一部分，同样要接受威胁建模和权限测试。

## 九、怎样验收链路追踪是否真的有用

挑选几类已知故障做演练：旧政策被检索、工具参数错误、写入成功但回执丢失、模型超时、人工交接中断。请未参与开发的人只凭 Trace 回答：哪个版本、哪一步、输入了什么证据、外部动作是否发生、下一步该查哪里。若仍需要登录五个系统拼时间，追踪并没有完成任务。

还要测试上下文传播。让请求跨 HTTP、消息队列和异步任务，确认父子关系不断；检查并行 Span 时间是否正确；故意制造敏感字段，确认采集前已被删除；改变采样规则，确认高风险事件仍能保留。

一条好的 Trace 不承诺自动找出所有根因。它提供的是可验证的时间线与证据，让团队少猜几次、少重现几轮，并把真实失败变成离线回归样本。能从一句错答追到具体证据和具体版本，链路追踪才算真正工作。

## 十、先从一条关键路径开始

刚起步不必把每个函数都变成 Span。先选一条事故频繁、结果可核对的业务链路，记录请求入口、检索、关键工具、状态写入和最终结果，并统一任务标识与版本字段。拿最近三次真实故障回放：如果值班同学能在一个界面分清“没有调用”“调用失败”和“调用成功但结果被误用”，第一版已经产生价值。之后再依据排障盲区增加粒度，而不是为了图好看把时间线塞满。

上线前再做一次跨边界测试：请求从网关进入，经模型服务、检索服务和消息队列，最后由异步任务写入业务系统。逐段确认关联标识没有丢，时钟差不会颠倒顺序，失败重试仍指向同一业务动作。对于可能重复消费的消息，Trace 还应显示幂等键和实际回执，便于判断“重试了”与“重复写入了”的区别。

查询入口也要贴近真实排障：允许从工单号、任务号或告警安全跳转到对应轨迹，并保留访问审计。若只能先知道 Trace ID 才能查 Trace，值班时仍会卡在第一步。

这一步常比再加十个埋点更实用。
