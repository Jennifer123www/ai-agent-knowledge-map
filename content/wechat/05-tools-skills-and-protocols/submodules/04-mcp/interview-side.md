# 面试题：MCP 的协议边界和兼容性怎么答

![MCP 协议面试图解](./assets/mcp-cover.png)

总概览里只需要说清“协议负责连接，不负责业务授权”。这一篇把问题继续往下拆：数据层和传输层是什么，发现和版本协商解决什么，远程服务怎样做安全和兼容。

## 问题 1：MCP 的数据层和传输层分别负责什么？

### 原理

数据层定义客户端和服务器之间交换消息的结构与语义，包括版本、能力发现、工具/资源/提示等对象和请求响应。传输层负责消息如何建立连接、分帧、发送和认证，例如本地标准输入输出或远程 HTTP。

![MCP 数据层与传输层](./assets/mcp-layers.png)

### 答题点

1. 数据层关心“交换什么、代表什么”；
2. 传输层关心“通过什么通道、怎样建立和保护连接”；
3. 同一对象语义可以落在不同传输上，部署形态和安全要求却不同；
4. 业务授权、凭据和后端错误不能因为协议分层就消失。

### 记忆点

> 数据层定语言，传输层修道路。

### 追问

为什么不直接用 REST？REST 可以是 Server 内部或外部的业务接口；MCP 增加了面向 AI 应用的能力发现、对象语义和交互约定。两者可以叠加，不是互斥替代。

### 失分点

把 MCP 说成一种部署方式，或把 HTTP、JSON-RPC 和业务 API 混成同一层。

## 问题 2：MCP 的能力发现和版本协商怎样工作？

### 原理

客户端连接服务端后，需要知道对方支持的协议版本、对象类型和可用能力，再据此决定后续调用。服务端能力变化时，客户端还要更新缓存和策略，而不是继续使用旧目录。

![MCP 连接与能力发现](./assets/mcp-discovery.png)

### 答题点

1. 连接时交换身份、版本和能力摘要；
2. 客户端读取工具、资源或提示目录，结合本地权限做筛选；
3. 双方选择共同支持的版本，不支持时明确失败或降级；
4. 目录变化、参数变化和服务版本要可观测、可回归和可回滚。

### 记忆点

> 先确认能说哪种语言，再看手里有哪些能力。

### 追问

能力目录能否完全信任？不能。目录只是服务端声明，客户端还要核对来源、授权、风险和本地策略；工具返回的内容也应视为不可信数据。

### 失分点

只说“连接后列工具”，没有版本、缓存失效、能力变更和权限筛选。

## 问题 3：本地 MCP 和远程 MCP 的工程差异是什么？

### 原理

本地 Server 通常是同机进程，低延迟、便于访问本地资源，但进程权限和启动配置靠近用户机器。远程 Server 可服务多个客户端，更适合共享业务能力，但需要网络、认证、租户隔离、限流和可用性治理。

![本地与远程 MCP](./assets/mcp-local-remote.png)

### 答题点

1. 本地重点防止进程越权、路径越界、恶意配置和本地数据泄露；
2. 远程重点处理认证、授权、租户、网络超时、重放和并发；
3. 两者都需要能力发现、参数校验、审计和版本兼容；
4. 迁移部署形态不能只改地址，还要重新设计信任边界和凭据传递。

### 记忆点

> 本地靠进程边界，远程靠身份和网络边界。

### 追问

远程 Server 能否代表用户访问所有后端？不应默认。应传递用户或委托身份，按租户、资源和动作授予最小权限，并在后端再次校验。

### 失分点

只比较延迟，不讲远程认证、租户隔离、重连和审计；或认为 HTTPS 等于业务授权。

## 问题 4：MCP 为什么不等于授权系统？

![MCP 的认证与授权边界](./assets/mcp-security.png)

### 原理

协议规定客户端和服务器如何交互，但不能替业务系统判断一个用户能否读取某条记录、修改某个订单或删除某个文件。认证确认身份，授权决定能力范围，执行层还要校验参数和当前状态。

### 答题点

1. 连接认证确认 Client、Server 和用户上下文；
2. 能力目录按身份和任务过滤，避免暴露无权能力；
3. 每次 Tool 调用重新检查资源归属、风险和审批；
4. Resource 读取同样需要脱敏、审计和撤销，不能只保护写操作。

### 记忆点

> MCP 规定怎么敲门，业务系统决定谁能进哪间房。

### 追问

工具列表里不展示危险工具是否足够？不够。服务端仍需防止直接调用、目录缓存过期、权限变化和参数越界。

### 失分点

说“Server 暴露了工具，所以 Client 就拥有工具权限”，把发现能力误认为授权结果。

## 问题 5：MCP 连接如何做兼容性测试？

![MCP 版本兼容与回滚](./assets/mcp-compatibility.png)

### 原理

兼容性不只是连接成功。要覆盖版本协商、能力发现、对象列表、读取/调用、错误、超时、断线恢复和权限拒绝。服务端或工具契约变化，都可能影响上层技能。

### 答题点

1. 建立协议握手和能力发现的固定回归用例；
2. 对 Tools、Resources、Prompts 分别验证语义、参数和返回；
3. 模拟版本不匹配、目录变化、断线、重复请求和限流；
4. 将服务端版本、客户端版本和能力摘要写入 Trace，支持灰度和回滚。

### 记忆点

> 兼容测试测的是整条交互，不是只测“能连上”。

### 追问

工具增加可选字段会破坏兼容吗？取决于客户端和 Schema 处理方式；仍应通过真实客户端回归。删除字段、改变枚举语义和修改副作用通常风险更高，需要版本或迁移方案。

### 失分点

只测试正常路径，没有测试版本、错误、权限、重连和能力变更。

## 问题 6：MCP 远程返回内容可能包含提示注入，怎么办？

### 原理

远程 Resource、Tool 结果和 Prompt 模板都可能带有不可信文本。客户端应把它们当作数据，不能让返回内容覆盖系统策略、擅自改变权限或诱导调用其他工具。

### 答题点

1. 区分协议元数据、业务数据和不可信指令，不盲目提升优先级；
2. 对返回内容做来源、敏感信息和格式检查；
3. 工具调用仍经过本地允许列表、参数和审批；
4. 记录可疑内容与调用链，必要时阻断 Server、撤销凭据或转人工。

### 记忆点

> 连接可信不等于内容可信。

### 追问

为什么 Server 是内部部署也要防？内部账号、文档和依赖同样可能被误配、污染或被攻击；信任需要分层，不能只看网络位置。

### 失分点

只靠系统提示词说“忽略恶意指令”，没有在客户端和执行层设置硬边界。

## 问题 7：MCP 的请求、响应和通知怎样区分？

### 原理

请求需要对方处理并返回与调用 ID 对应的响应；通知用于报告变化，不要求逐条响应。能力目录变化、进度和状态事件适合通知，但客户端应按订阅和频率控制接收。

### 答题点

1. 每个请求有稳定标识，响应按标识匹配，不依赖返回顺序；
2. 超时后保留请求和后端任务关联，避免未知状态下重复执行；
3. 通知是变化信号，客户端按需重新读取目录或状态；
4. 对长任务使用任务句柄、进度、取消和结果获取，不长期占用同步连接。

### 记忆点

> 请求要答案，通知报变化，长任务给句柄。

### 追问

通知丢失怎么办？客户端不能只依赖通知维护真相，应能重新读取权威目录或任务状态；通知用于加速更新，不是唯一状态源。

### 失分点

把所有交互都当同步 RPC，没有超时、重复、通知丢失和长任务处理。

## 问题 8：协议无状态与 Agent 有状态是否矛盾？

### 原理

协议请求自描述，便于独立处理和重试；Agent 任务仍可在运行时保存会话、审批、工具结果和检查点。协议无状态不等于业务没有状态，而是状态要显式管理。

### 答题点

1. 请求携带版本、身份和必要能力信息，不依赖隐藏连接上下文；
2. 业务状态放在数据库或任务运行时，用任务 ID 显式引用；
3. 重复请求按幂等键和权威状态处理，不能靠进程记忆去重；
4. 断线恢复后重新建立连接、发现能力并读取任务状态。

### 记忆点

> 协议消息自描述，业务状态显式存。

### 追问

为什么显式状态更适合扩容？请求可以路由到不同实例，重启后也能恢复；状态若只在某个进程内存里，会造成粘性连接和丢失风险。

### 失分点

把无状态解释成“Server 什么都不记录”，忽略长期任务、审计和后端业务状态。

## 问题 9：MCP Server 不可用时怎样降级？

### 原理

降级要看能力性质。只读信息可以在允许时使用带时间戳缓存，高风险写操作在身份或状态不明时应停止，非关键能力可以临时关闭并明确告知用户。

### 答题点

1. 区分只读、可重试写入和不可逆动作；
2. 缓存必须带来源、版本和更新时间，不能伪装实时；
3. 连接失败采用有限重连和退避，避免雪崩；
4. 降级、关闭和人工接管都写入任务状态与告警。

### 记忆点

> 能安全降级的才降级，不能确认的写操作宁可停。

### 追问

是否可以自动切换到另一个 Server？可以，但要验证能力契约、身份、数据范围和结果语义一致，并记录切换事件。备用服务不是同名就等价。

### 失分点

把重连当作唯一策略，或在服务不可用时让模型用记忆替代实时业务结果。

## 问题 10：什么时候不需要 MCP？

### 原理

协议引入运行、认证、版本和观测成本。单应用、少量内部函数、稳定部署边界的场景，直接工具接口可能更简单。跨客户端复用、独立能力提供方和动态发现增多时，MCP 的收益才明显。

### 答题点

1. 评估客户端和能力提供方数量，是否存在重复适配；
2. 判断是否需要独立部署、动态目录和跨团队契约；
3. 比较协议治理收益与新增运维、认证和兼容成本；
4. 可先用内部 Tool 接口验证，再在复用需求出现时封装 Server。

### 记忆点

> 连接规模需要共同语言时再上协议，不为协议而协议。

### 追问

一个 Server 暴露很多能力是否更省事？部署可能更少，但权限面、故障范围和版本耦合会扩大。应按安全域、团队边界和生命周期拆分，不按数量机械合并。

### 失分点

认为所有工具都必须通过 MCP，或者只谈生态热度，不谈系统规模和维护成本。

答到这里，可以顺手补一句：采用 MCP 是架构选择，不是能力证明。系统最终仍要用任务成功率、接入维护成本、安全事件和兼容性故障来判断是否值得。

## 收束答法

MCP 的价值是把 AI 应用连接外部能力时的共同语言定下来，包含数据层的对象和语义，也包含传输层的连接方式。生产落地还要补上版本协商、能力发现、认证、最小授权、错误处理和兼容测试。它让接入更统一，却不会替业务系统自动发权限，也不会替你证明远端内容可信。
