# 大话主管调度：组长不能只会转发消息

公司要选一家数据平台，主管 Agent 把任务分别发给市场、技术和财务专家。三个人很快交回材料：市场说增长快，技术说接口多，财务说价格有优势。主管把三段话按顺序粘在一起，得出“建议采购”。整个过程看上去分工明确，实际上没有统一范围、没有证据验收，也没处理价格优势建立在哪个用量假设上。

主管模式的关键，不是多一个会说“收到”的角色，而是始终掌握总目标、状态和控制权。它要把目标拆成可验收任务，按能力和权限选择专家，检查交付，发现冲突后补证，在预算耗尽时停下，最后生成统一答案。只转发消息的主管，顶多是一台昂贵的群聊机器人。

## 一、主管为什么不能只是转发消息

用户面对的是一个统一入口，希望得到完整、口径一致的答复。专家只处理局部任务，不知道所有约束。主管若原封不动转发用户长消息，专家会自己猜重点；若原封不动拼接专家回答，用户又要替系统做合并。拆分与验收正是主管存在的理由。

主管还负责控制信息范围。财务专家只需报价和规模假设，技术专家只需需求与测试环境，市场专家不需要看到合同底价。把完整上下文广播给所有人既浪费，也扩大数据暴露。主管应生成最小任务包，并记录每个专家拿到了哪个版本。

控制权也要清楚。主管调用专家时，专家完成后返回结果，最终答复仍由主管给出；这与任务交接不同。若专家能直接接管用户会话、随意派人，系统容易出现多个角色争抢下一步，排查起来像在办公室里追问“这事现在到底谁负责”。

## 二、总目标怎样拆成可验收子任务

“评估供应商”太宽。主管先提取最终决策需要的维度：市场稳定性、技术适配、三年成本、合规风险。再识别依赖：三年成本需要用户规模，技术适配需要统一场景，合规风险可能需要人工或专业服务。每个子任务都必须产出最终报告可直接使用的字段。

![主管下发任务时的五项契约](./assets/supervisor-contract.png)

拆分不是均匀切块。技术验证可能比市场检索耗时，应该给更多预算；合规若只是检查两项硬要求，可以交给规则或人工，不必专门启动一个自由 Agent。子任务边界应由数据、工具、权限和验收决定，不由组织架构或角色名字决定。

主管还要防止重叠。市场和财务都可能查定价，前者关心定价策略，后者关心可复算成本。任务单应明确各自口径，并规定冲突交回主管。否则两个专家各算一套，最后多了重复成本，仍没有可用数字。

## 三、专家选择和路由依据是什么

专家路由不只看任务关键词，还要看能力、工具、权限、当前负载、历史质量和成本。技术核验应选择能访问试用环境且具备对应评测脚本的 Agent；财务核算要读取受限报价，但不必获得测试环境凭据。若自动专家连续失败，应转到人工或备用流程。

![专家路由的四类判断依据](./assets/supervisor-routing.png)

可以维护能力目录：每位专家声明支持的任务类型、输入 schema、输出 schema、工具与权限、费用和限制。主管先按硬条件过滤，再按质量、延迟和成本排序。模型可辅助理解自然语言任务，但最终权限检查由运行时执行，不能因为路由模型说“适合”就临时放大权限。

路由还应可解释。日志至少记录候选专家、选择理由、被拒绝的硬条件和任务版本。若结果不好，才能判断是任务拆错、路由错，还是专家执行错，而不是把所有责任归给“模型不稳定”。

## 四、任务契约怎样限制输出和权限

一张任务单包括任务标识、目标、输入引用、交付格式、证据要求、权限、预算、停止条件和失败原因。技术专家收到的不是“看看 A 厂商行不行”，而是“在指定版本上验证三项场景；返回步骤、结果、日志引用、未知项；只操作隔离测试环境；最多调用十次工具”。

输出 schema 可以要求 status、findings、evidence、unknowns、conflicts 和 next_action。主管先做结构校验，再读内容。缺证据的“已完成”应判为未通过，权限外动作应被执行层拦截。契约不是礼貌提醒，而是运行时接口。

预算也写进任务。专家不应无限搜索到“绝对确定”，也不能因首次失败就草草交付。达到最低证据标准即可返回；资料确实缺失时，清楚说明缺口也是合格结果。主管必须允许“无法确认”，否则专家只会被迫编一个答案。

## 五、主管怎样验收而不是照单全收

主管收到结果后，先检查任务是否覆盖、字段是否齐全、证据能否访问、来源是否一手、时间和版本是否匹配。价格要复算，工具结果要看业务回执，高风险判断要进入人工关卡。文笔流畅不属于核心验收条件。

![主管保留控制权并验收专家结果](./assets/supervisor-principle.png)

*图参考 [OpenAI Agents SDK 的 manager 模式](https://openai.github.io/openai-agents-python/multi_agent/) 与 Anthropic 的 orchestrator-workers 模式改绘。主管保留统一控制权，专家作为受限子任务执行者返回结果。*

验收失败要给出具体缺口：缺少某版本文档、价格没有税费、测试没有失败日志，而不是笼统说“再深入一点”。具体反馈才能让下一轮产生新信息，也便于判断是否值得继续。若失败来自任务单本身含糊，主管要先修任务，而不是反复责令专家重做。

合并时统一口径。市场用年度、财务用月度，技术用海外版，必须在写最终报告前调整。无法统一的内容要标成限制或分歧，不可被一句“综合来看”抹平。

## 六、证据冲突时怎样追问和补证

技术专家说支持私有化部署，财务专家引用的价格表却只包含云服务。主管先检查双方是否在讨论同一产品版本，再回到一手文档或让专家补证。冲突可能源于事实错误，也可能源于口径不同，直接挑一个答案会把问题藏起来。

![主管处理冲突的补证流程](./assets/supervisor-conflict.png)

补证任务要小而明确：“确认 2026 企业版是否支持私有化，并给出官方部署文档；不要重新写完整技术报告。”这样控制成本，也减少新一轮引入无关结论。若官方资料本身矛盾，记录两个来源、联系日期和对决策的影响，交由人判断。

多数投票不适合解决事实冲突。多个模型可能引用同一转载，也可能共享相同偏差。能用工具复算的数字就复算，能用试验验证的能力就试验，剩下的价值判断才讨论权重。

## 七、怎样防止重复委派和无限循环

主管给每个任务生成指纹，包含目标、输入版本和关键参数。相同指纹已完成时复用结果；正在运行时不重复派发；失败后只有在策略、输入或专家发生变化时才允许再试。否则系统可能在“请补充证据”和“资料不足”之间来回打转。

![每轮委派都要产生可验收增量](./assets/supervisor-budget.png)

每轮结束检查增量：新增了哪条证据，解决了哪个未知项，还是只换了说法。连续两轮没有有效增量，应停止、换工具或转人工。运行时还维护最大委派次数、总轮次、token、工具、时间和金额；硬上限不依赖模型自觉。

防循环也要防“循环换人”。主管依次问三个相同能力的专家，仍没有独立来源，只是把同一问题重复消费。路由策略应识别失败原因：资料不存在时换模型没有用，权限不足时需要授权或人工，参数错误时修输入即可。

## 八、预算、超时和人工升级怎样控制

预算按任务风险和价值分配。关键安全测试可以多给工具次数，市场背景只需少量检索；专家有单步超时，主管有总截止时间。慢分支如果不是硬依赖，可以带缺口结束；若是采购决策必需项，主管停止推荐并请求人工补充。

高风险动作进入人工升级：联系供应商、提交采购、使用敏感报价、决定合规例外。主管只能准备材料和提议动作，运行时保存当前状态，人工批准后再继续。审批必须绑定具体任务、金额、版本和有效期，一句脱离上下文的“可以”不够。

降级方案同样重要。某专家不可用时可以退回固定工作流或单 Agent；状态存储异常时禁止写操作；预算耗尽时交付阶段性报告。少做一些并标明缺口，比在控制失效时继续自动化更稳。

## 九、怎样评测主管本身

主管评测不能只看最终报告。要分别统计任务拆分覆盖率、路由准确率、任务契约完整度、专家结果采纳是否正确、冲突发现率、重复委派率、无效轮次、预算超支和人工升级是否及时。最终答案好，可能只是某个专家很强；主管价值要单独证明。

构造资料完整、资料冲突、缺权限、专家超时、专家返回无证据结论、同一任务重复唤醒等案例。检查主管是否选择正确路径，是否把失败归因到正确环节，是否在必要时停下。还要与固定路由或简单规则基线比较，避免用复杂模型解决一张能力表就能解决的问题。

上线后抽样审查路由理由和验收记录，关注长尾循环与成本。主管 Agent 成熟的标志不是它能调动多少专家，而是它让每次委派有理由、每份交付能验收、每个冲突能追溯、每轮继续都有新增价值。

## 十、先让主管只管一件事

首次上线时，可以让主管只负责“选择市场、技术或财务专家并生成任务单”，最终验收仍由人完成。路由稳定后，再开放结构校验和低风险合并；涉及价格、合同与采购动作的决定继续由人工把关。逐步扩大职责，能把路由错误、专家错误和验收错误分开观察，也避免一个尚未评测的主管同时拥有拆分、执行和批准三种权力。

当某条路由规则已经很稳定，例如所有价格复算都交给同一个确定性服务，就把它固化，不必每次由模型选择。主管应该把注意力留给真正变化的任务，而不是为了证明自己“聪明”，反复决定已经有标准答案的事情。
