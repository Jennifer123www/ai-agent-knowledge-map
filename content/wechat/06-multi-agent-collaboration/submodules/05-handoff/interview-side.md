# 面试题：Handoff 怎样换人又不丢状态

面试官给出客服退款场景：分诊 Agent 已核对订单和身份，退款 Agent 接手后不能从头提问；高金额退款要人工批准；任何超时都不能产生两张退款单。Handoff 不只是“把消息发给另一个 Agent”，它考察控制权、状态、权限和副作用怎样一起转移。

## 问题 1：Handoff 与工具调用或专家调用有什么区别

**原理：**调用时原 Agent 保留控制权，另一个 Agent 返回结果；Handoff 时新 Agent 接管后续会话和任务责任。

**答题点：**查询退款政策可调用专家；后续持续核验原因、生成草稿并与用户沟通，适合交接。设计时明确 active_agent、交接原因、接管后的权限和返回条件。若只是一次性问答，不必切换控制权。

![主管调用与任务交接的控制权区别](./assets/handoff-control.png)

**记忆点：**调用交结果，交接交责任。

**常见追问：**交接后能否再交回？可以，但要带状态变化与理由，并限制重复往返。

**失分点：**只说“handoff 是 transfer_to_xxx 工具”，没有解释语义。

## 问题 2：最小交接包应包含哪些字段

**原理：**交接要让新 Agent 继续工作，又要避免广播全部历史和敏感数据。交的是当前任务快照，不是完整聊天复制。

**答题点：**task_id、用户目标、已确认事实及来源、输入版本、已执行动作与回执、未决问题、下一步、允许工具、禁止动作、预算、有效期和交接原因。大文件与敏感信息传受控引用；明确记录尚未发生的动作。

![Handoff 的最小上下文包](./assets/handoff-package.png)

**记忆点：**目标、事实、回执、缺口、权限、下一步。

**常见追问：**是否传完整聊天？仅在确有需要且符合权限时提供引用，默认传结构化摘要和必要原文片段。

**失分点：**只传最后一句“用户想退款”，或把所有历史数据全部广播。

## 问题 3：怎样过滤交接输入，防止隐私和指令污染

**原理：**不同角色拥有不同数据需求与权限；用户文本和外部内容也不能被误当系统指令。过滤应由应用层执行。

**答题点：**按 schema 白名单选择字段，敏感值掩码或引用；接收方按需通过授权工具读取；区分系统策略、业务事实、用户文本和外部内容的信任等级；删除与新任务无关的历史；记录谁传了什么字段。凭据永不放进自然语言上下文。

**记忆点：**最小数据、最小权限、明确信任边界。

**常见追问：**模型自己总结能否脱敏？可辅助识别，但最终字段过滤和权限必须由确定性代码实施。

**失分点：**认为内部 Agent 之间天然可信，可以共享全部信息。

## 问题 4：控制权怎样原子地切换

**原理：**交接过程中若原 Agent 和新 Agent 同时执行，可能重复提交；若两边都认为对方负责，任务会悬空。

**答题点：**生成唯一 handoff_id；先准备并持久化交接包；接收方校验并返回 accepted；运行时使用版本检查更新 active_agent；成功后原 Agent 停止新动作；重复投递返回同一结果；拒绝或过期时仍由原 Agent 或人工持有责任。

![上下文与控制权一起转移](./assets/handoff-principle.png)

**记忆点：**先确认接住，再松手；整个过程只有一个负责人。

**常见追问：**一定要分布式事务吗？未必，可用状态机、幂等事件和条件更新实现可恢复的一致语义。

**失分点：**发出消息就认为交接成功，不等待接收确认。

## 问题 5：新 Agent 如何恢复而不重复提问

**原理：**新 Agent 先读取并核对交接状态，补问未知项；已确认事实可复用，但过期和无来源字段要重新验证。

**答题点：**检查 task_id、状态版本、关键业务回执、有效期和权限；向用户简短复述目标与下一步；只询问 pending_questions；外部状态可能变化时调用查询工具；尚未执行的动作明确标记，不能凭摘要宣称完成。

![新 Agent 接管后的确认与恢复](./assets/handoff-resume.png)

**记忆点：**复用已确认，补问真缺口，先核对再行动。

**常见追问：**交接摘要与外部系统不一致听谁的？外部权威状态与业务回执优先，同时记录差异并修正状态。

**失分点：**为了保险把所有问题重问一遍，或为了流畅盲信过期摘要。

## 问题 6：人工审批怎样嵌入交接

**原理：**人工参与是带检查点的暂停与恢复，不是把工单扔出系统。批准针对具体动作和状态版本。

**答题点：**Agent 生成动作提议与证据，保存状态并暂停；人工看到订单、金额、理由和影响后批准、拒绝或修改；记录身份、时间、决定和有效期；恢复前检查状态是否变化；执行后写业务回执。拒绝走明确分支。

![人工审批与任务恢复](./assets/handoff-human.png)

**记忆点：**人批准的是这次动作，不是给 Agent 一张长期通行证。

**常见追问：**审批等待很久怎么办？相关事实带有效期，恢复时重新查询订单与支付状态。

**失分点：**一条“同意”消息没有绑定任务、金额和版本。

## 问题 7：交接超时、拒绝或重复投递怎么办

**原理：**网络失败会造成发送方和接收方认知不一致。交接需要明确生命周期和幂等标识。

**答题点：**handoff 状态包括 prepared、accepted、rejected、expired；超时查询状态后有限重试同一 handoff_id；接收方按 id 去重；拒绝返回缺失字段或不匹配原因；不可用时进入人工队列或由原 Agent阶段性交付，不临时放大权限。

**记忆点：**超时先查谁持有责任，再决定重试。

**常见追问：**用户重复点击如何处理？用业务 task_id 和交接 id 去重，返回现有处理进度。

**失分点：**每次重试都创建一个新 Agent 和一张新退款单。

## 问题 8：怎样避免 Agent 之间来回踢皮球

**原理：**角色边界模糊或拒绝条件重叠，会形成循环交接。运行时要识别重复状态与无增量转移。

**答题点：**为每个角色定义接收条件与拒绝码；记录交接路径和状态指纹；相同状态重复回到同一角色时停止；限制最大交接次数；要求再次交接必须新增事实或改变任务类型；冲突转人工或主管裁定。

**记忆点：**没有新事实，就不要再换一位问同样的问题。

**常见追问：**如何区分合理退回和循环？合理退回带具体缺失字段或新状态，循环只是同一输入在角色间往返。

**失分点：**只提高 max_turns，让“踢皮球”持续更久。

## 问题 9：如何评测一次 Handoff

**原理：**交接质量同时涉及任务连续性、用户体验、权限安全和副作用。只看最终回答是否正确不够。

**答题点：**测试正常、缺字段、过期状态、拒绝、超时、重复投递、人工批准与业务变化；统计重复提问率、关键事实保留、错误状态、越权调用、交接时延、人工补充和重复副作用；核对任一时刻只有一个 active_agent；检查最终动作有业务回执和完整追踪。

**记忆点：**用户不用重讲，系统不丢事实，权限不越界，动作不重复。

**常见追问：**怎样做隐私测试？在原会话放置与退款无关的敏感字段，断言交接包和新 Agent 日志中不存在。

**失分点：**只验证新 Agent 能生成一句自然的接场话。

Handoff 设计题可以用“包、权、验、回”来收束：准备最小上下文包，唯一地切换控制权，新角色先核验状态，高风险动作通过人工并留下业务回执。这样换人不等于重启任务，也不会把责任丢在两个 Agent 中间。

## 现场交接题怎样从正常路径讲到故障

先讲正常路径：分诊 Agent 根据退款意图生成 handoff_id，把订单引用、身份核验结果、物流状态、未决原因、允许工具和“尚未创建退款单”写进交接包。退款 Agent 校验输入后返回 accepted，运行时用版本条件把 active_agent 切换过去，原 Agent 随即停止。用户只需补充真正未知的退款原因。

然后把三个故障插进去。第一，accepted 响应丢失：发送方先查询 handoff_id 状态，不新建第二个任务。第二，物流在交接期间变为已发货：接收方核对外部状态，交接包中的旧事实被标为过期，任务进入新的规则分支。第三，退款已创建但本地回执未保存：恢复时按业务键查询，不能再次提交。

再讲权限与人工。交接只传白名单字段，完整支付信息通过受控工具按需读取；高金额退款保存检查点后暂停，审批绑定订单、金额、状态版本和有效期。批准回来先检查业务是否变化，再执行并记录真实退款回执。模型生成一句“已退款”不能作为完成依据。

最后给评测指标：重复提问率、关键事实保留率、交接接受时延、错误 active_agent、敏感字段泄露、重复副作用和人工补充量。测试拒绝、超时、重复投递和来回交接，确保任一时刻只有一个负责人。这样回答不仅解释了 API，也覆盖任务连续性和安全边界。

若面试官问“如何实现原子切换”，不必夸口跨系统事务。可以用持久化状态机：prepared 时原 Agent 仍负责但不得再发起冲突动作；接收方校验成功后，以状态版本为条件写入 accepted 和新的 active_agent；写入失败说明已有其他变化，重新读取；事件重复消费则按 handoff_id 返回既有结果。

接收方拒绝时要给机器可读原因，例如字段缺失、任务类型不支持、权限不足或状态过期。原 Agent 根据原因补字段、改路由或转人工，而不是把同一包原样再投一次。拒绝原因本身也进入追踪，帮助发现角色边界设计是否长期不清。

再补充用户体验边界：新 Agent 可以简短确认已掌握的订单和下一步，但不要展示内部角色名、链路编号或一长串系统术语。透明是让用户知道责任已经转移、当前还缺什么，不是把编排细节全部倒给用户。

安全收尾可以强调撤权：任务结束、交接撤销或超时后，临时访问令牌和敏感数据引用应失效；新 Agent 不能把一次退款任务的权限带到下一段无关对话。状态连续不等于授权永久连续。

还可以补一个审计视角：最终记录应回答交接由谁发起、接收方何时确认、当时传了哪些字段、哪一版状态生效、人工批准了什么、真实业务回执是什么。发生投诉时能沿这条链还原现场，才算交接闭环；只有自然语言聊天，往往只能看见大家都说自己“处理过”。

责任可追溯，交接才不只是一次消息转发。

用户不必重讲，系统也不应重做。
