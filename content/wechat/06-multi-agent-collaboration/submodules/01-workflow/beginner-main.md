# 大话工作流：路已经画好，模型负责哪一段

小周出差回来，要把机票、酒店和打车票整理成报销草稿。他只希望系统读取票据、核对标准、说明超标项，再生成一份待确认草稿，不要自动提交。这个任务里既有识别图片、理解备注和写说明，也有金额计算、制度判断和系统写入。若把全部事情交给一个 Agent 自由决定，灵活是灵活，哪一步漏了、哪一次重复提交了，也更难说清。

工作流适合这种“路大致知道，只是个别站点需要模型”的任务。它把步骤、先后关系、分支和失败出口预先画好，再把模型放进确实需要语言理解的节点。模型不是整条流水线的厂长，更像其中一位擅长读票据和写说明的同事。

## 一、报销草稿为什么不需要多个 Agent 自由讨论

报销规则通常是明确的：票据属于哪类、日期是否在出差期间、金额是否超过标准、哪些字段必填。系统也知道最终交付只是草稿。因此更合适的路径是读取申请、解析票据、校验规则、生成说明、人工确认。路径稳定，分支也能列举，没有必要让多个角色围绕每张发票展开讨论。

![差旅报销草稿的固定工作流](./assets/workflow-fixed-path.png)

固定并不意味着僵硬。缺票据可以走补充资料分支，金额超标可以走人工审批分支，识别失败可以让用户手动确认字段。所谓固定，是变化发生时允许走哪些路已有边界，而不是让模型临场编一套流程。

这也带来一个好处：任务失败时能定位到节点。是图片没读清、制度版本错了、计算有误，还是提交接口超时，各自有不同处理方式。若所有逻辑都藏在一段大提示词里，系统只会得到一个“不太对”的最终答案，修起来像在一锅汤里找哪粒盐放多了。

## 二、节点、边和条件分别表示什么

节点是一段可执行工作，例如“读取票据”“查询报销标准”“生成超标说明”。边表示允许从一个节点走到另一个节点。条件决定走哪条边，例如票据齐全进入金额校验，票据缺失则进入补充资料。结束节点也要明确：生成草稿并等待确认，或因资料不足安全停止。

节点的粒度要能独立验收。把“处理报销”作为一个节点太粗，无法判断哪里出错；把每个字段读取拆成几十个节点又会让编排开销过大。合适的节点应有明确输入、可观察输出、超时和失败类型。比如“制度校验”输入结构化金额与城市，输出适用标准、差额和制度来源。

边还代表依赖。没有确认出差日期，就不能判断发票是否在行程内；票据金额可以并行识别，但总额必须等必要结果到齐。图上箭头不是装饰，它应该对应真实的数据需求和控制顺序。

## 三、模型节点和确定性代码怎样分工

图片里的模糊文字、员工写的自然语言备注、超标原因的简洁说明，适合模型处理。金额相加、日期比较、税率计算、字段格式和权限判断，更适合代码或规则引擎。后者有唯一或可枚举答案，没必要让语言模型“凭语感算一下”。

![确定路径怎样包住不确定模型](./assets/workflow-principle.png)

*图参考 [Anthropic 的 Agent 工作流模式](https://www.anthropic.com/engineering/building-effective-agents) 改绘。核心不是某个框架，而是用可检查的输入输出包住不确定的模型节点。*

模型读取票据后，应先返回结构化字段和不确定项，而不是直接写“已核验无误”。代码再检查金额格式、日期范围和必填项。模型写完说明后，代码检查是否包含申请编号、超标金额和待确认标记。这样允许模型在表达上有弹性，却不把金额和权限也交给它发挥。

如果模型置信不足，输出可以进入人工确认，而不是自动选择一个数字。把“不确定”设计成正常分支，比事后要求模型永不出错更实际。确定性边界越清楚，模型就越能专心做自己擅长的部分。

## 四、条件分支怎样处理缺票据和超标准

小周少了一张酒店发票，系统应指出缺哪天、缺哪个字段，并停在“等待补充”，而不是继续推测住宿金额。若酒店金额超过制度标准，系统先计算差额，再判断是否存在已批准的例外；没有例外就生成超标说明并交人工审批。两种异常都不能塞回正常直线。

![报销工作流的正常与异常分支](./assets/workflow-branching.png)

条件要尽量来自可核数据。不要写“如果看起来合理就通过”，而要写“票据日期在行程范围内、金额不超过对应城市与职级标准、申请字段齐全”。模型可以辅助把制度文字映射成结构化规则，但实际路由最好由明确条件执行。

分支还要有汇合规则。补齐票据后可以回到制度校验，人工批准超标后可以进入草稿生成；审批拒绝则结束并说明原因。若没有明确回路，系统可能补完资料后从头重跑，或在拒绝后仍沿旧状态提交。

## 五、重试为什么必须配合幂等键

读取网页失败后再试一次，通常只是多花一点时间；提交报销失败后再试一次，却可能创建两条申请。更麻烦的是：服务端其实已经成功，客户端只是在等待回执时超时。此时系统看到的是“没有收到成功”，不等于“操作没有发生”。

![危险重试与幂等重试的区别](./assets/workflow-idempotency.png)

安全做法是为同一次业务请求生成幂等键，并在重试前查询既有状态。服务端若已处理该键，返回原回执，不再创建新记录。若外部系统不支持幂等，至少要保存请求摘要和业务标识，先查是否存在同一申请，无法确认时转人工，不要闭眼再点一次。

“最多重试三次”并不能解决重复副作用。重试策略还要看错误类型：网络抖动可退避重试，参数错误应立刻修正，权限不足应停止，业务冲突应走分支。把所有错误都当临时故障，只会把一次错误稳定地执行三遍。

## 六、写操作失败后怎样补偿或停下

假设草稿已创建，附件上传失败。数据库回滚不一定能把外部报销系统里的草稿一起撤掉。工作流可以选择补偿：删除已创建草稿，或保留草稿并标记“附件未完成”；具体选哪种取决于业务是否允许删除、补偿动作是否可靠。

补偿不是时间倒流。邮件已经发出，无法真正回滚，只能再发更正；付款已经进入银行处理，撤销需要另一笔业务动作。设计工作流时，要为每个有副作用的节点列出回执、可否查询、可否补偿、补偿失败后由谁处理。

若系统无法判断草稿是否创建成功，最安全的结果可能是暂停并提示人工核对。自动化不要求任何故障都自行消化。知道何时不继续，比在状态不明时努力“完成任务”更重要。

## 七、状态、日志与回执怎样留下证据

一次运行至少需要统一的 run_id、当前节点、输入摘要、规则版本、模型版本、每步开始与结束时间、分支理由、工具请求标识和业务回执。日志不必保存所有敏感原文，但要让排查者回答：这份草稿使用了哪版制度，哪个金额由哪张票据产生，系统为何进入人工审批。

![工作流应留下的关键执行证据](./assets/workflow-observability.png)

模型输入输出要做脱敏和版本标记。员工身份证号、银行卡和完整发票原图不应随意进入通用日志；可以记录哈希、字段摘要或安全存储引用。规则版本也不能省略，否则制度更新后，很难解释昨天通过、今天超标的差异。

可观测性还要连接业务结果。模型返回“成功”不算回执，报销系统的申请编号和状态才算。若工作流结束时只有一段自然语言，就无法确认动作是否真实发生，也无法安全恢复。

## 八、什么时候固定流程开始不够用

若报销类型越来越多，规则由多个地区和项目动态决定，处理过程中还要根据资料临时寻找专家，固定分支可能迅速膨胀。这时可以在局部引入路由或 Agent：例如让模型识别异常类型，再选择合适的制度查询工具；但提交、审批和付款仍保持确定性关卡。

判断标准不是流程图看起来复杂，而是变化是否难以枚举、是否真的需要运行时规划。即使引入 Agent，也应把它放在有输入输出的节点中，并保留超时、预算、权限和验收。最常见的稳健结构是“外层工作流，内层 Agent”，而不是把整套业务交给一个无限循环。

反过来，若某段 Agent 行为逐渐稳定，也可以把它固化为工作流。架构不是单向从简单升级到复杂；成熟系统经常把验证过的自治步骤重新收紧，换取可预测性和更低成本。

## 九、怎样用案例集验收工作流

测试至少覆盖正常票据、缺票据、日期越界、金额超标、制度服务超时、草稿创建成功但回执丢失、附件上传失败和人工拒绝。每个案例都检查走过哪些节点、分支理由、模型与工具调用次数、最终状态以及是否产生重复副作用。

还要做故障注入：在写入前、写入后和保存回执前分别中断，再恢复运行。若系统能从可信状态继续，不重复创建草稿，说明幂等与检查点确实工作；若每次都从第一步重来，只是流程图画得漂亮。

上线先保持“只生成草稿”。观察错误分布和人工修改，确认制度映射、异常分支和日志足够可靠，再考虑开放受控提交。好的工作流不靠模型永远聪明，而是让正常步骤清楚、异常有出口、写操作有回执、失败之后还能说明白发生了什么。

## 十、把工作流交给运营前再看一眼

最后做一次“人能不能接手”的检查：页面要显示当前节点、等待原因和最近业务回执；异常要告诉运营该补什么，而不是只给一串错误码；人工修改后，系统应从受影响节点继续，不必整条重跑。流程若只有开发者看得懂，出了问题仍会把所有工单推回技术团队。可运行只是第一关，可解释、可接管、可恢复，才算真正进入业务。
