# 大话多智能体协作：三支小队怎样合成一份报告

公司要在三家供应商里选一个长期合作伙伴。老板只给了一句话：“市场前景、技术风险、三年成本都看一下，周五给我结论。”市场资料散在公开报告里，技术参数藏在文档和试用记录中，报价又分一次性费用、订阅费和超额计费。一个助手当然也能从头查到尾，但任务一长，资料容易串，数字容易漏，最后还可能用一段流畅的文字把三个口径不一致的结论粘在一起。

于是有人提议：多开几个 Agent，一个看市场，一个看技术，一个算钱，再让主管 Agent 汇总。听上去像给 AI 组了个项目组，实际上只是把一个难题拆成了更多可能出错的接口。多智能体真正增加的不是“人多热闹”，而是独立上下文、并行执行、专业工具和相互验收；同时也增加通信、等待、冲突、权限和成本。先把这笔账算明白，再谈协作。

## 一、先别急着组队，看看一条链路够不够

如果供应商名单固定、评分表已经写好、数据都在同一张表里，最稳的方案通常是固定工作流：依次读取字段、按规则计算、让模型写摘要、最后由人确认。这里的“工作流”指预先规定好的步骤和分支，不需要几个角色自由讨论。它便于测试，失败也容易定位，像一条标好站点的地铁线。

只有当子任务确实需要不同资料、不同工具或不同权限，而且能够独立验收时，多智能体才可能划算。比如市场 Agent 只读行业资料，技术 Agent 使用试用环境，财务 Agent 读取受限报价；三者可以同时工作，且每份交付都能单独检查。若三项工作每一步都互相等待，拆成三个人只会多出三套上下文和一堆来回确认。

![从简单结构到自治协作的选择](./assets/orchestration-choice.png)

一个实用顺序是：先做单 Agent 基线；路径稳定后固化成工作流；遇到长任务中断，再加入状态与检查点；只有独立分工能带来明显收益时才加多 Agent；需要运行时决定由谁处理，再加主管调度；控制权确实要换人时，才用任务交接。复杂度应被问题“挣出来”，不该由架构图的气势决定。

## 二、五个子模块分别解决什么问题

工作流解决“已知步骤怎样稳定执行”。状态与任务图解决“做到一半怎样知道自己在哪，并从可信位置继续”。多智能体协作解决“可独立的任务怎样分工并汇合”。主管调度解决“运行时怎样拆任务、选专家、验收结果”。任务交接则解决“下一位 Agent 或人工接管后，怎样继承目标、事实、权限和未决问题”。

它们并非五套互斥产品。供应商选型可以先用固定工作流收需求和候选名单；把任务状态写进检查点；主管再把市场、技术、财务三份任务单交给专家；专家完成后返回证据；高风险结论由采购负责人确认。此时外层路径是确定的，内层调研允许一定自治，人工关卡保留最终责任。

容易混淆的是“主管调用专家”和“Handoff（任务交接）”。主管调用专家时，主管仍面对用户，专家像一个能力更强的工具，完成子任务后把结果交回来；任务交接则把后续对话和责任交给新角色，例如客服分诊 Agent 把退款任务交给退款 Agent。前者是请人办一件事，后者是正式换负责人。

## 三、子任务必须写成能验收的任务契约

主管若只说“查一下 A 厂商的技术情况”，技术 Agent 很容易返回一篇产品介绍。合格的任务单至少写清目标、输入范围、交付格式、证据要求、权限边界、截止条件和失败出口。例如：“核对 2026 年 9 月仍在售版本；比较可用区、备份恢复和审计能力；每项给出一手来源及发布日期；不能确认的地方列为未知；只读资料，不联系销售。”

![一份可验收的任务契约](./assets/orchestration-task-contract.png)

契约的重点不是把提示词写得很长，而是让上下游对同一个“完成”达成一致。市场 Agent 的完成可能是三项趋势和各自来源；财务 Agent 的完成是统一币种、税费和三年假设；技术 Agent 的完成是满足项、风险项和需要试验的未知项。三份交付结构相近，主管才能合并；事实口径不同，也能在冲突发生时追到源头。

任务契约还应规定什么不能做。调研可以读取公开网页，不代表可以注册试用、给供应商发邮件或下载受限客户数据。若专家缺少关键资料，正确结果是“资料不足，并说明需要什么”，不是靠常识补出一个看起来完整的答案。把权限和失败出口写进契约，是在任务开始前阻断幻觉和越权。

## 四、顺序、并行、主管和交接怎么选

顺序结构适合有明确依赖的步骤：先确认三年规模，再计算费用；规模没定，后面的数字没有意义。并行结构适合彼此独立的任务：市场、技术、财务可同时查，最后再合并。主管结构适合子问题数量或类型要等运行后才知道的任务，例如发现某厂商使用特殊许可后，临时增加法务核查。交接结构适合职责真正改变，例如售前 Agent 发现问题进入合同谈判，交给法务 Agent 继续与用户沟通。

![四种协作结构的适用条件](./assets/orchestration-patterns.png)

不要把所有步骤都并行。三名专家若都需要同一份尚未确认的需求清单，应该先收齐需求；否则每个人会用自己的假设开工。也不要为了“互相验证”让三个 Agent 做完全相同的检索，再用多数票决定事实。不同 Agent 可能共享同一个错误来源，三票并不比一条一手证据更可靠。

实际项目常是混合结构：需求澄清顺序执行；三路调研并行；主管动态补派一个许可专家；最后把高风险决策交给人。设计时先画数据依赖和控制权，再选模式。若先决定“我们要做多 Agent”，很容易让任务去迁就架构。

## 五、共享状态不是把聊天记录扔进群里

协作需要公共信息，但不需要所有角色看到全部对话。共享状态应保存任务目标、版本化需求、已分配任务、交付物、证据索引、未决问题、预算和动作回执。专家拿到与自己相关的最小上下文，既减少干扰，也降低敏感数据扩散。财务报价不必出现在市场 Agent 的上下文里，技术试用凭据更不该被其他角色顺手继承。

状态中的事实要有来源和时间。比如“A 厂商支持跨区域备份”不能只写成布尔值，还要记录来自哪份文档、适用于哪个版本、何时读取。需求变化时，系统才能判断哪些结论失效，而不是把旧资料继续当新事实。共享状态更像项目账本，不像一张不断向后复制的聊天长截图。

并行写入还会带来冲突。市场 Agent 和技术 Agent 可能同时更新同一厂商卡片，若直接覆盖，后完成的人会抹掉先完成的字段。解决办法可以是分区字段、追加事件、带版本号的条件写入，或由主管统一合并。关键不是选哪种数据库，而是明确谁能改什么、冲突如何被发现。

## 六、主管要验收，不能只负责转发

主管 Agent 的职责包括拆分、路由、预算、验收和合并。它收到技术 Agent 的结论后，应检查是否覆盖任务单中的全部维度、证据能否打开、版本和日期是否匹配、未知项是否被藏在漂亮措辞里。若两名专家结论冲突，先核对口径，再要求补证；不能用“哪个写得更自信”决定。

![主管与专家的委派验收闭环](./assets/orchestration-principle.png)

*图依据 [AutoGen](https://arxiv.org/abs/2308.08155) 的多 Agent 对话框架，以及 OpenAI Agents SDK 的编排方式改绘。这里强调工程中的任务契约、证据交付与验收，并非照搬论文的某个固定拓扑。*

主管也会出错。它可能把相同任务重复派给专家，收到空结果后无限追问，或为了凑齐报告擅自补全未知数据。因此运行时要记录任务指纹、已委派次数、是否产生新证据和剩余预算。连续两轮没有新增信息，就应该停下、换策略或请人处理，而不是让 Agent 互相客气地再聊十轮。

最终合并也不是简单拼接。市场增长、技术风险和三年成本可能使用不同时间范围。主管应把比较口径统一，在结论旁保留证据和限制，并把“已确认”“推断”“未知”区分开。读者看到的不只是推荐谁，还能知道推荐建立在哪些事实之上。

## 七、错误为什么会沿协作链放大

一个 Agent 把“支持备份”误读成“支持跨区域自动恢复”，下游财务 Agent 可能据此删掉灾备成本，主管又把低成本写成推荐理由。原始错误经过计算和总结后，表面上越来越完整，追查却越来越难。链路越长，越不能只在末尾检查文风。

阻断错误要在接口处做。每个专家交付结论时附证据和适用范围；主管合并前进行结构校验和关键事实抽查；涉及价格、合规和不可逆动作时，调用确定性工具或人工复核。对于没有来源的数字，系统应降级为未知，而不是让下一位 Agent 继续计算。

还要保留来源血缘：最终报告中的某一行价格来自哪个文件、哪一版汇率、哪次计算。这样修正一个输入时，可以定位受影响的结论。若所有中间内容都被压成一段自然语言，任何改动都可能迫使整条链从头重跑。

## 八、四类预算决定协作何时停下

多 Agent 的预算不只有 token。调用预算限制最多启用几名专家、每人允许多少轮；时间预算限制单步超时和总等待；风险预算规定哪些操作必须人工确认；错误预算规定连续失败几次后停止自动尝试。四类预算都应由运行时计数，不能只在提示词里写“请不要反复调用”。

![多智能体协作的四类预算](./assets/orchestration-failure-budget.png)

供应商调研中，技术 Agent 若已经找到两份一致的一手文档，就没必要再浏览二十篇转载；财务 Agent 遇到报价口径缺失，应尽早列出需要采购补充的字段；主管发现三家都缺合同条款时，可以先交付阶段性报告，而不是假装任务仍在自动推进。停止是一种正常结果，不是系统失败。

预算还帮助比较方案。如果多 Agent 只把报告从八十分提高到八十二分，却让成本翻四倍、等待从两分钟变成二十分钟，就不一定值得。相反，若它显著提高关键事实的覆盖率和证据完整度，即使稍慢，也可能适合高风险采购。

## 九、怎样证明这支队伍真的比一个 Agent 好

先准备一组固定案例，包含资料齐全、资料冲突、价格缺失、版本过期和服务超时。让单 Agent 与多 Agent 在同一输入、同一权限、同一验收标准下完成任务。比较任务成功率、事实错误、证据可追溯性、遗漏项、总时延、模型与工具成本，以及人工介入次数。只看“文章更长”“分析更全面”不够。

评测还应拆到角色和接口：主管是否把任务派对了人，专家是否遵守范围，交付是否带来源，冲突是否被发现，预算耗尽后是否安全停止。端到端失败时，能指出是哪一环出错，才有改进价值。否则每次都只能换个更大模型碰碰运气。

上线时从低风险、可回退的任务开始。先让系统只生成供应商报告草稿，不自动发邮件、不修改采购系统；观察一段时间后，再开放受控写入。多智能体协作的成熟标志，不是屏幕上有多少个会说话的角色，而是每份任务有边界、每个结论有证据、每次动作有回执、每条链路知道何时停。
