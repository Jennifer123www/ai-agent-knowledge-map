# 面试题：多 Agent 何时值得用

面试官让你比较三款客服产品。你提议用市场、技术、财务三个 Agent 并行，面试官马上会问：为什么一个 Agent 不行？三份结果如何合并？结论冲突听谁的？成本翻倍是否值得？下面九道题专门考察“多 Agent 本身”，不把主管路由、状态存储或固定工作流细节混在一起。

## 问题 1：什么时候多 Agent 优于单 Agent

**原理：**优势来自任务可独立、可并行、需要不同上下文或工具、且能单独验收；劣势来自通信、合并、额外调用和更多失败点。

**答题点：**三路产品调研资料源不同、技术验证需要试用工具、财务数据有独立权限，适合拆分；若只是对同一张表计算评分，单 Agent 或代码更合适。先建立单 Agent 基线，再用质量、证据、时延和成本证明收益。

![任务是否适合多 Agent 的判断矩阵](./assets/multiagent-fit.png)

**记忆点：**独立性、专长差异、并行收益、可验收，缺一项都要谨慎。

**常见追问：**上下文太长是不是理由？是候选理由，不是充分条件；先做检索、压缩和分段，边界清楚后再拆角色。

**失分点：**回答“多个模型互相纠错，所以一定更准”。

## 问题 2：子任务边界怎样划分

**原理：**好的边界减少跨角色依赖，并让产物可作为稳定接口。按组织岗位照搬角色，未必符合数据和验收边界。

**答题点：**先列最终报告所需字段和依赖，再按数据来源、工具权限与验收标准分组。可按产品拆，也可按专业拆；技术指标需统一试验时按专业更好，资料完全独立时按产品更好。每个任务写目标、输入版本、输出 schema、证据和停止条件。

**记忆点：**按信息和验收拆，不按角色故事拆。

**常见追问：**拆得越细越好吗？不是。过细会让通信与调度开销超过任务本身，合并也更难。

**失分点：**每个 Agent 只负责写一段文字，却无法独立验证。

## 问题 3：并行和顺序怎样选择

**原理：**没有数据依赖的任务可并行，存在前置结果的任务必须顺序或分阶段。并行收益受最慢分支和汇合成本限制。

**答题点：**三家公开资料可并行；统一需求和测试脚本先完成；成本测算等待坐席规模；最终推荐等待关键事实。为分支设置 deadline，可选分支超时带缺口继续，关键分支超时暂停。避免对相同工具无限并发造成限流。

![多 Agent 并行协作与统一汇合](./assets/multiagent-parallel.png)

**记忆点：**先画依赖，再开并行；并行不是所有节点一起跑。

**常见追问：**并行三倍调用一定三倍快吗？不一定，还受服务限流、最慢分支、合并和重试影响。

**失分点：**忽略共享前置条件，让各分支基于不同假设开工。

## 问题 4：Agent 之间应该传什么

**原理：**协作接口应传可验证产物，不必传完整聊天或隐藏思考。信息越多不代表越好，可能放大噪声和泄露范围。

**答题点：**传任务标识、输入版本、结构化结论、证据引用、计算假设、未知项、冲突项、动作回执和建议下一步。大文件传受控引用；自然语言只负责必要说明。接收方先校验 schema、版本和权限，再使用结果。

![结论、证据、范围与未知项组成交付](./assets/multiagent-evidence.png)

**记忆点：**传产物，不传一整脑袋草稿。

**常见追问：**何时需要原始对话？审计或解释特定决策时按权限读取，不应默认广播给所有角色。

**失分点：**让 Agent 互相转发整段上下文，直到超出窗口。

## 问题 5：共享状态怎样避免污染

**原理：**多个 Agent 写同一状态会产生覆盖、过期结果和权限扩散。状态应分区、版本化并保留来源。

**答题点：**按角色或任务使用命名空间；共享需求使用版本号；并行更新采用乐观锁、事件追加或主管归并；每条事实带来源与时间；最小权限控制读取；过期任务的结果不能进入新版本汇合。敏感凭据永不进入共享文本状态。

**记忆点：**公共事实可共享，私有凭据和无关过程要隔离。

**常见追问：**放向量库能解决吗？不能。向量库解决相似检索，不自动提供并发控制、字段版本和授权。

**失分点：**只讲 Memory，不讲一致性、来源和访问控制。

## 问题 6：错误怎样沿链路放大

**原理：**上游错误会被下游当事实继续计算和总结，最后更完整也更难察觉。多 Agent 增加了错误传播接口。

**答题点：**在每个交付边界做 schema 校验、证据检查、关键数字复算和适用范围核对；保留数据血缘；未知项不进入确定结论；高风险字段使用独立工具或人工验证；限制错误产物被广播。评测错误首次出现在哪个角色和接口。

**记忆点：**下游的流畅不能洗白上游的错误。

**常见追问：**再加一个批评 Agent 是否有效？只有它具备独立标准、独立证据或确定性检查时才有意义。

**失分点：**把模型自评当事实验收。

## 问题 7：结论冲突怎样裁定

**原理：**冲突可能来自事实错误，也可能来自版本、范围、时间和评价权重不同。处理顺序是先统一口径，再补证，最后才是决策。

**答题点：**比较来源层级和发布时间；检查产品版本、地区、币种、计费周期和样本范围；要求双方给出可复核证据；无法消除时保留分歧及影响；高风险冲突交人工。事实问题不用多数票，偏好问题可展示不同权重下的结果。

**记忆点：**先问是不是在说同一件事，再问谁对。

**常见追问：**能否按 Agent 历史准确率加权？可以作为辅助，但不能替代当前证据，也要防任务分布变化。

**失分点：**让主管选择“更自信”的答案。

## 问题 8：预算与停止条件怎样设置

**原理：**多 Agent 容易出现重复检索、互相追问和尾部等待。停止条件需要运行时硬限制与增量判断。

**答题点：**限制总轮次、每个分支的 token、工具调用、时间、金额和失败次数；为任务生成指纹，拦截重复派发；连续若干轮没有新证据则结束或转人工；定义最低交付标准和关键分支 deadline；预算耗尽时返回已有结果与缺口。

**记忆点：**每轮都要产生新证据，否则就是付费闲聊。

**常见追问：**不同分支预算一样吗？不必。按风险、复杂度和对最终结论的贡献分配，并可在汇合前动态调整。

**失分点：**只写 max_turns，不处理工具成本、总超时和人工升级。

## 问题 9：怎样做单 Agent 与多 Agent 的对照评测

**原理：**多 Agent 天然使用更多计算；必须在相同任务、数据和权限下比较净收益，并关注稳定性与长尾。

**答题点：**用正常、资料缺失、来源冲突、工具失败和越权诱导案例；比较任务成功率、事实准确、证据覆盖、冲突发现、人工修改、总延迟和成本；重复运行观察方差；按任务拆分、专家产物、合并和最终答案分层归因。设定上线阈值与回退方案。

![单 Agent 与多 Agent 的对照指标](./assets/multiagent-evaluation.png)

**记忆点：**同题、同尺、同权限；质量提升还要扣掉协作成本。

**常见追问：**多 Agent 只在复杂样本更好怎么办？用路由器识别复杂样本，普通任务走简单方案，并单独评测路由误判。

**失分点：**只展示一次漂亮对话，没有基线、样本量和成本。

回答多 Agent 题时，先证明任务值得拆，再说明怎样独立交付、怎样限制共享、怎样解决冲突，最后用对照评测闭环。架构图上角色再多，也替代不了这些边界。

## 现场系统设计题怎样完整展开

可以从单 Agent 基线开场：先让一个 Agent 在统一需求下完成三款产品调研，记录事实错误、证据覆盖、时延和成本。然后指出技术试验、市场资料和三年成本使用不同工具与权限，且能分别验收，因此拆成三个并行任务；最终推荐仍等待三路关键字段到齐。这段先证明“为什么拆”。

接着画共享状态，但不要画一间所有人都能说话的聊天室。状态里只有需求版本、任务单、结构化交付、证据和预算；每个 Agent 使用独立上下文和最小权限。技术 Agent 返回测试步骤与日志，财务 Agent 返回假设与可复算表，市场 Agent 返回来源和样本范围。合并器先查版本和 schema，再读自然语言说明。

![独立 Agent 怎样经共享状态汇合](./assets/multiagent-principle.png)

面试官若问冲突，就拿“官网标价与合同报价不同”举例：先统一币种、税费和计费周期，再回到一手来源；无法统一就保留两个场景，不用多数票。若问循环，就说明任务指纹、最大轮次和新增证据检查；没有新增事实的互相追问会被运行时终止。

最后给出评测：相同模型、工具和案例集对比单 Agent 与多 Agent，至少看事实准确、证据覆盖、冲突发现、总延迟、总成本和人工修改。重复运行观察方差，并按任务拆分、专家执行和合并三个阶段归因。若提升只出现在少量复杂样本，就加路由按需启用，而不是让所有请求都养一支团队。

还可以主动说明降级：任一专家不可用时，非关键分支带缺口交付，关键分支回退到单 Agent 或人工；共享状态异常时禁止产生副作用。多 Agent 故障面更大，设计答案若只有正常并行而没有降级，说明系统还停在演示阶段。

若被问到通信拓扑，点对点适合边界清楚的少量协作，广播容易污染上下文，黑板式共享状态便于汇合但需要并发和权限控制，主管式拓扑便于统一验收但可能成为瓶颈。没有永远最好的拓扑，选择依据仍是依赖、控制权与验收。

最后提醒可观测性：每个任务保留父子 run 关系、输入版本、工具回执和成本，最终结论可追到具体专家与来源。否则系统即使偶尔答对，也无法解释是哪个环节带来收益，更无法在回归时定位退化。

上线策略也值得主动提：先让多 Agent 只生成草稿，在少量复杂样本上观察冲突、成本和人工改动；达到阈值后再扩大流量。若服务或状态层异常，回退单 Agent 或固定流程，并保留已有证据。能按需启用、也能安全关闭，才说明多 Agent 是一项工程能力，而不是无法拆除的展示功能。

这也是架构取舍最实际的证据。
