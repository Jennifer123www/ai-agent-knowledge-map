# 面试题：状态图怎样恢复任务又不重做危险动作

面试场景是一份长时间运行的研究报告：功能、价格和数据政策分支并行，途中可能关机、等待用户或遇到工具超时。系统恢复后要接着做，却不能重复发送审批、覆盖并行结果或把旧资料当新事实。九道题重点不在会不会调用某个图框架，而在状态和副作用能否被清楚解释。

## 问题 1：任务状态与聊天历史怎样区分

**原理：**聊天历史记录说过什么，任务状态记录当前哪些事实成立、哪些动作发生、下一步允许做什么。聊天可辅助模型理解，不能独自承担恢复和一致性。

**答题点：**状态应结构化保存目标版本、当前节点、子任务状态、来源、产物引用、未决问题、预算、外部回执和人工决定。聊天作为审计或语境输入，可被压缩和裁剪；状态字段则由节点和运行时更新，并接受 schema 与权限约束。

![任务状态对象的核心字段](./assets/stategraph-state-object.png)

**记忆点：**聊天是会议录音，状态是项目看板。

**常见追问：**能否让模型每轮总结聊天当状态？可用于生成候选摘要，但关键字段和动作回执必须由程序校验、从工具结果写入，不能只信模型自述。

**失分点：**回答“把全部消息放数据库”，没有说明事实、计划和回执的区别。

## 问题 2：状态字段怎样建模

**原理：**状态要支持决策、恢复和审计，又不能把所有原始内容无限复制。字段应按稳定业务事实组织，而非按某次 Prompt 的段落组织。

**答题点：**分为 identity、goal、inputs、task_status、artifacts、evidence、pending_questions、action_receipts、budget、control 和 schema_version；大文件只存引用；事实记录来源、时间和适用范围；推断与计划单独存放；敏感字段按角色控制读取。字段更新最好有版本或事件记录。

**记忆点：**状态要回答“现在在哪、凭什么、做过什么、下一步是什么”。

**常见追问：**是否直接保存模型隐藏思考？不需要，也不应依赖。保存可验证输入、输出、理由摘要和证据即可。

**失分点：**把状态设计成一段不断增长的 summary，无法做条件判断和并发合并。

## 问题 3：转移守卫怎样避免非法跳步

**原理：**模型可以建议下一步，但运行时应验证从当前状态到目标节点的转移是否合法。守卫条件保护业务不变量。

**答题点：**定义允许的源节点、目标节点和条件，如“关键来源数达到要求”“价格口径已统一”“人工批准存在且未过期”。守卫由结构化字段和确定性规则执行；失败时返回缺失条件，进入补证、等待或失败态，而不是默默跳过。

![任务状态与转移守卫](./assets/stategraph-transition.png)

**记忆点：**模型提议去哪，守卫决定能不能去。

**常见追问：**复杂条件能否由模型判断？可以辅助解释非结构化资料，但最终高风险转移应由代码、规则或人工确认。

**失分点：**只在 Prompt 里写“必须先审批”，运行时却没有阻断。

## 问题 4：检查点何时保存，保存什么

**原理：**检查点是可恢复的一致状态，不是定时截图。保存太早会记录未完成动作，保存太晚会丢失昂贵结果。

**答题点：**在可独立验收的节点成功后、昂贵工具完成后、外部写操作回执到达后和人工中断前保存。内容包括状态版本、节点输出引用、已完成节点、外部回执、预算与下一节点。检查点写入本身应原子化，并关联稳定 thread_id 或 run_id。

![状态、回执与下一步组成检查点](./assets/stategraph-checkpoint.png)

**记忆点：**节点完成、回执落盘，再宣布可恢复。

**常见追问：**模型生成一半要不要检查点？一般不把半段输出当正式结果；可记录诊断信息，恢复时从完整输入重跑该节点。

**失分点：**只保存当前节点名称，没有输入版本、产物和副作用回执。

## 问题 5：并行更新怎样解决冲突

**原理：**并行分支基于同一旧版本读取，再写同一对象，会发生丢失更新。合并策略取决于字段是否独立、是否可交换以及谁拥有最终决策权。

**答题点：**独立子任务写各自命名空间；共享字段采用乐观锁和版本号；可追加信息使用事件日志；汇合节点检查必需分支、口径和冲突；无法自动合并时保留两个版本并转人工。任何覆盖都应可追踪，不用“最后写入者胜出”掩盖冲突。

**记忆点：**先分区，再版本；能自动合并就合并，不能就显式冲突。

**常见追问：**分布式锁是不是最简单？锁能串行化部分写入，但增加等待和故障处理，不解决语义冲突；仍要定义合并规则。

**失分点：**回答用 Redis 锁，却说不清两份不同口径的研究结论怎么处理。

## 问题 6：失败恢复为什么不能盲目重放

**原理：**本地没记录成功，外部动作可能已经发生。读操作、纯计算和写操作的重放语义不同，恢复前要核对真实状态。

**答题点：**节点声明 safe、idempotent、query-before-retry 或 manual-only；恢复时读取最后检查点，查询外部业务回执，确认动作是否发生；幂等写入复用稳定键；不可确认的邮件、付款和审批转人工。资料检索可重做，但要记录资料时间变化。

![故障恢复的三步判断](./assets/stategraph-recovery.png)

**记忆点：**恢复先对账，再重放。

**常见追问：**如何实现 exactly-once？跨系统通常很难保证严格恰好一次，应说明用幂等、去重、回执和补偿达到业务上可接受的语义。

**失分点：**把“从最后节点继续”理解为无条件再次调用最后一个工具。

## 问题 7：人工中断后如何继续原任务

**原理：**人工参与是带状态的暂停与恢复。审批信息必须成为任务状态的一部分，而不是散落在另一段聊天里。

**答题点：**中断前保存提议动作、证据、当前状态和恢复节点；生成审批请求；人工批准、拒绝或修改时记录身份、时间和决定；恢复前检查决定是否过期、输入是否变化；用同一任务标识继续。拒绝应走明确分支，不能再次提出同一动作。

**记忆点：**暂停冻结现场，恢复先验证现场。

**常见追问：**等待期间外部价格更新怎么办？将相关字段标记过期，恢复时回到核验节点，而不是直接沿旧决定执行。

**失分点：**人工回复一句“可以”就触发动作，没有关联具体任务、金额和版本。

## 问题 8：图版本和状态版本怎样迁移

**原理：**流程图、状态 schema、规则和 Prompt 会独立变化。新代码直接读取旧检查点可能找不到节点，或错误解释缺失字段。

**答题点：**每次运行记录 graph_version、state_schema_version、rule_version 和 prompt_version；旧任务继续旧版本，或通过显式迁移函数转换；迁移校验关键字段，缺失事实时回到补证而非填默认；重大风险升级时暂停旧任务并人工处理；保留迁移日志和回退策略。

**记忆点：**迁移的是运行中的事实，不只是 JSON 结构。

**常见追问：**蓝绿发布能否解决？能隔离新旧流量，但运行中长任务仍要绑定旧版本或迁移，不能只切入口。

**失分点：**只说数据库加字段，没有考虑节点重命名、守卫变化和外部副作用。

## 问题 9：如何用故障注入验收状态图

**原理：**正常路径无法证明恢复正确。需要在关键边界主动中断，检查状态、回执与实际业务是否一致。

**答题点：**在节点执行前后、检查点写入前后、外部写成功但本地超时、并行合并、人工等待和版本迁移时注入故障；恢复后断言已完成步骤是否复用、不可重放动作是否重复、状态版本是否连续、冲突是否显式、预算是否继承。还要模拟同一任务被重复唤醒。

![状态图的读取、守卫、执行和检查点闭环](./assets/stategraph-principle.png)

**记忆点：**不拔一次“电源”，就不知道检查点是真是假。

**常见追问：**线上能做故障注入吗？先在测试和影子环境做，生产只对低风险路径、受控比例和可回退故障进行演练。

**失分点：**只看恢复后的最终文本，不核对外部系统是否出现重复记录。

状态图面试题可以用四句话收束：状态保存事实与回执，守卫限制合法转移，检查点提供一致恢复，重放策略保护副作用。再补上并行冲突、人工暂停和版本迁移，回答就从“会画图”进入“能运行”。

## 现场恢复题可以怎样推演

面试官若说“报告生成到一半机器宕机”，先不要直接回答从检查点重跑。第一步问清最后检查点包含什么，第二步核对外部系统里有没有已经发生的写操作，第三步按节点重放策略决定继续。只读检索可以重做，保存草稿使用稳定文档标识，发送审批则先查询业务回执，状态不明就转人工。

再画一个小状态对象：目标版本、当前节点、三个分支的完成状态、来源引用、待确认数字、动作回执和预算。功能与价格分支分别写自己的命名空间，汇合时检查产品版本。若其中一个分支基于旧需求完成，版本守卫会拒绝它进入新报告，而不是靠最后写入者覆盖。

人工审批题也用同一状态解释：暂停前保存提议动作和恢复节点，审批绑定具体状态版本，等待期间若价格变化则标记过期。恢复不是“把同一 Prompt 再发一次”，而是先验证现场，再从合法转移继续。最后补上故障注入测试，说明你不仅设计了恢复，也知道怎样证明它真的安全。

如果面试官继续追问存储实现，可以说明检查点记录与大产物分离：状态库保存版本、节点、引用和回执，大文件放受控对象存储；写检查点使用条件更新，防止两个执行器同时推进。同一 thread_id 被重复唤醒时，只有持有正确版本的一方能提交下一状态，另一方读取新版本后停止或重新判断。

还可以补充清理策略：完成任务保留必要审计记录，临时网页、截图和敏感模型日志按期限删除；恢复能力不等于永久保存所有内容。这样状态设计同时覆盖可靠性、并发与合规，而不只是选一个数据库名字。

最后说明状态机并不会让模型变确定，它只是把不确定步骤放进可观察、可暂停、可恢复的边界中。
