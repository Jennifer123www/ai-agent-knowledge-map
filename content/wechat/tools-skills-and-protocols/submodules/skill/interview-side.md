# 面试题：Skill 怎样从流程说明变成可运行能力

![技能子模块面试图解](./assets/skill-cover.png)

总览文章已经讲过 Skill、Tool 和协议的三层关系。面试时不要再停在“Skill 是一组工具”这句话上。真正值得展开的是：一项技能如何被选中，如何知道自己做对了，出了问题如何恢复，改了版本如何保证不把旧流程弄坏。

## 问题 1：Skill 和 Tool 的边界怎样划分？

### 原理

Tool 是一个可调用动作的契约，描述输入、输出和副作用；Skill 是一套面向任务的执行方法，描述什么时候使用、按什么步骤做、用哪些工具和资料、产出什么结果。Skill 可以编排多个 Tool，也可以包含人工判断和验收步骤。

### 答题点

1. 以责任范围划分：Tool 负责原子动作，Skill 负责任务流程；
2. 以复用方式划分：Tool 可被多个流程调用，Skill 面向一类完整任务复用；
3. 以验收方式划分：Tool 检查参数和返回值，Skill 检查中间产物与最终交付物；
4. 以权限方式划分：Skill 描述方法不能自动放大权限，Tool 执行前仍需按调用者身份校验。

### 记忆点

> Tool 是遥控器上的一个按钮，Skill 是把一件事办完的操作手册。

### 追问

一个脚本什么时候算 Skill？如果脚本只是接收参数并完成一个动作，它更像 Tool；如果脚本连同适用条件、步骤、资料、异常处理和验收要求一起组成任务方案，才更接近 Skill。分类看使用责任，不看文件后缀。

### 失分点

把 Skill 说成“更大的 Tool”，却没说明流程、验收和人工节点；或者认为写进 Skill 的动作就天然获得权限。

## 问题 2：技能发现怎样避免选错？

![技能发现与匹配](./assets/skill-discovery.png)

### 原理

技能发现通常分两步：先从轻量目录中找候选，再读取完整说明执行。目录需要提供名称、适用任务、输入要求、禁用条件和预期产物，不能只有一句宽泛的介绍。

### 答题点

1. 建立可区分的技能描述，明确对象、动作和产物；
2. 用任务类型、组织、权限和风险过滤候选；
3. 缺少关键输入时先追问，不让模型用猜测补齐；
4. 记录匹配结果和未选原因，用真实任务评测技能选择准确率。

### 记忆点

> 先缩小候选，再读完整手册；能发现不等于能执行。

### 追问

多个技能都能处理同一请求时怎么办？可以按优先级、版本、权限和成本排序，也可以让路由器先做分类。不要把所有技能说明一起放进上下文，否则选择错误和上下文成本会同时上升。

### 失分点

只说“让大模型自己选择”，没有输入过滤、权限筛选、候选评测和无匹配时的停止策略。

## 问题 3：怎样验证一个 Skill 真的执行正确？

![技能、工具与结果的关系](./assets/skill-method-tool.png)

### 原理

技能的成功不是模型说“完成了”，而是交付物通过一组可检查的验收标准。评测要覆盖步骤是否完整、证据是否存在、外部动作是否成功和最终任务是否达成。

### 答题点

1. 为技能定义输入、过程产物、最终产物和完成条件；
2. 对确定性内容用程序校验，例如字段、金额、格式、引用和状态；
3. 对开放性内容结合样本、模型评分和人工抽检，校准评分器；
4. 记录技能版本、工具版本、输入来源和轨迹，支持失败定位与回归。

### 记忆点

> 技能要验收产物，不验收模型的语气。

### 追问

为什么“工具调用成功率”不能代表技能成功？因为工具可能调用了错误对象，也可能只完成了中间步骤。账单查询成功，不代表异常解释和报告交付完成；创建工单成功，也不代表问题已经解决。

### 失分点

只给一个端到端分数，不拆选择、参数、步骤、证据、权限和最终交付，出了问题无法定位。

## 问题 4：Skill 版本升级怎样避免回归？

![技能版本与验收](./assets/skill-versioning.png)

### 原理

Skill 的依赖不仅是代码，还包括提示模板、工具契约、数据字段、外部规则和验收标准。版本升级要把这些依赖作为一个发布包管理，并用代表性任务回归。

### 答题点

1. 记录版本、变更范围、依赖版本和迁移说明；
2. 用常见、边界、对抗和高风险任务组成固定回归集；
3. 在沙盒或小流量中比较质量、成本、延迟和安全事件；
4. 保留上一稳定版本，发现问题后能够回滚并解释受影响任务。

### 记忆点

> 技能改了方法，也要重新考试。

### 追问

技能版本与模型版本怎样关联？每次执行轨迹都应记录二者，必要时还记录工具模式和知识版本。否则同一技能换了模型后行为变化，无法判断根因。

### 失分点

只给技能文件加一个版本号，却没有回归集、灰度、回滚和依赖锁定。

## 问题 5：技能执行中断后怎样恢复？

![技能的检查点与恢复](./assets/skill-recovery.png)

### 原理

长流程需要检查点。每完成一个已经验收的阶段，就保存状态、产物、版本和下一步位置。恢复时重新检查会变化的外部事实，并对写操作使用幂等键。

### 答题点

1. 按阶段保存检查点，而不是只在流程结束时保存；
2. 区分临时错误、永久错误、权限错误和未知状态；
3. 恢复前重新查询库存、权限、订单等可能变化的事实；
4. 对已产生副作用的步骤先查状态，再决定重试、补偿或人工接管。

### 记忆点

> 从最近一次验收过的产物继续，不从头猜一遍。

### 追问

为什么不能简单把上一轮消息重新发给模型？消息不等于状态，外部动作可能已经发生，重复执行会造成副作用。恢复需要状态快照、任务 ID、幂等键和权威系统查询。

### 失分点

只讲指数退避，不讲检查点、状态查询和部分成功；或者把所有失败都交给模型“再试一次”。

## 问题 6：Skill、Prompt 和 Workflow 怎样区分？

### 原理

Prompt 主要约束一次或一类模型请求的目标和表达；Workflow 负责节点、状态、分支、等待与恢复；Skill 负责一类任务的完整做法，可以引用 Prompt，也可以由 Workflow 承载。三者可以组合，但不能互相代替。

### 答题点

1. Prompt 适合描述目标、规则和输出格式，不适合作为权限边界和状态存储；
2. Workflow 适合持久化的多步骤流程，能处理分支、重试、等待和停止；
3. Skill 关心任务方法、资源和验收，可以是静态手册，也可以绑定脚本或工作流；
4. 设计时根据任务稳定性、状态长度和风险选组合，不要求所有技能都做成复杂流程图。

### 记忆点

> Prompt 说怎么回答，Workflow 管怎么流转，Skill 管这类事怎么做完。

### 追问

什么时候一个 Skill 应该升级成持久化 Workflow？当任务跨较长时间、依赖外部事件、需要人工等待、存在可恢复节点或有副作用时。一次性的短任务没必要为了“看起来工程化”强行引入状态机。

### 失分点

把三者都解释成“提示词模板”，或者认为有了 Workflow 就不再需要技能说明和验收标准。

## 问题 7：复合任务中怎样编排多个 Skill？

### 原理

多个 Skill 协作时，重点不是让它们轮流输出长文本，而是定义清楚输入、产物、依赖、权威状态和验收。上层计划或工作流负责顺序与冲突，各技能保持职责内聚。

### 答题点

1. 按独立产物和复用边界拆分技能，避免巨型技能；
2. 用结构化产物交接，携带来源、版本、置信度和未完成项；
3. 指定共享数据的权威来源和写入顺序，防止互相覆盖；
4. 上层统一管理预算、权限、停止条件和最终验收。

### 记忆点

> 技能各自交作业，上层负责排课表和验收。

### 追问

怎样判断技能拆得太细？如果步骤没有独立产物、不能单独验收、也不会被其他任务复用，拆开只会增加调用轮次和错误点，可以合并到同一个技能内部。

### 失分点

只说“用多 Agent 编排”，却没讲技能之间的契约、状态冲突和最终责任；多几个角色并不会自动得到更清楚的系统。

## 问题 8：第三方 Skill 怎样做安全治理？

### 原理

Skill 会携带提示、脚本、资源和工具依赖，应当像软件包和策略配置一样治理。来源未知的技能可能访问敏感文件、诱导调用高风险工具，或通过资源内容影响模型判断。

### 答题点

1. 校验发布者、签名、版本、依赖和变更记录；
2. 安装前展示所需文件、网络、工具和业务权限，默认最小授权；
3. 脚本放入沙箱，外部文档按不可信输入处理，不能覆盖系统策略；
4. 保留执行审计、停用和撤销能力，发现问题后能定位受影响版本与任务。

### 记忆点

> 安装 Skill 不是导入一段文字，而是引入一份会影响行动的执行包。

### 追问

只允许内部员工编写是否就安全？不够。内部内容也会过期、误配或包含越权脚本，仍需代码审查、权限声明、回归评测和运行隔离。

### 失分点

只检查提示词是否有恶意内容，没有检查脚本、资源、依赖、工具权限和更新渠道。

## 问题 9：什么时候不应该做成 Skill？

### 原理

Skill 适合重复出现、步骤相对稳定、可以定义输入输出和验收标准的任务。一次性探索、规则尚未形成、强依赖临场判断的工作，过早封装只会把不成熟做法固定下来。

### 答题点

1. 任务只出现一次且没有复用价值时，直接完成比建技能更划算；
2. 关键规则频繁变化、连业务负责人都未达成共识时，先做人工流程和观测；
3. 任务主要是单个稳定动作时，提供 Tool 即可，不必包一层空技能；
4. 技能长期无人使用或评测持续退化时，应停用、归档并迁移依赖，而不是永远留在目录里。

### 记忆点

> 先有稳定做法，再封装技能；不要把试验稿刻成石碑。

### 追问

怎样判断一项技能值得维护？看调用频率、任务成功率、节省的人力、维护成本和风险。低频但高风险的技能也可能值得保留，不过需要更严格的审批和演练。

### 失分点

认为技能越多越代表平台成熟，没有考虑目录噪声、维护成本、权限面和废弃机制。成熟的平台也要敢于下架旧技能。

## 收束答法

如果只剩半分钟，可以这样答：Skill 是面向一类任务的可复用执行方法，包含适用条件、步骤、工具、资源、验收和失败处理。它与 Tool 的边界在于，Tool 做一个动作，Skill 组织一条流程。生产上要解决技能发现、权限隔离、过程验收、版本回归和中断恢复，不能把一份提示词文件直接当作可靠系统。
