## 1. 目标与边界

本项目以无需构建步骤的中文静态学习站为主体，并提供独立的微信公众号服务端接入和草稿生成工具。站点用同一套 AI Agent 知识体系服务两个阅读目标：

- **面向初学者**：建立全景认知，解释概念、结构、术语和模块关系。
- **面向面试**：将同一主题转为原理、答题要点、记忆点、图解与追问练习。

站点不承担运行 Agent、存储用户数据或调用模型的职责。HTML、内联 CSS 和原生 JavaScript 是站点唯一的运行时依赖；`site/` 是静态发布根目录。公众号接入代码位于 `api/`、`lib/wechat/`、`server/` 和 `scripts/`，仅在服务端运行。

规则：

1. 技术目录和程序文件使用小写英文，必要时用连字符，例如 `site-search.js`；公众号文章的 Markdown、提示词和图片放在对应系列目录。不要恢复旧的 `outputs/` 或 Word 终稿目录。
2. `content/wechat/` 下的一级模块目录使用两位序号前缀，格式为 `<nn>-<topic>`；`submodules/` 下的子模块也按各自 `series.json` 的 `seriesOrder` 使用 `<nn>-<child>`。序号只负责文件夹排序，`topic`、`submodule` 和组 `id` 等稳定标识不附加序号。
3. 新页面应放入明确的栏目目录，不要在 `site/` 根目录堆叠专题页。
4. 公共行为放入 `site/assets/js/`；仅被一个页面使用、且数据量不大的交互逻辑可留在该页面的内联脚本中。
5. 新增站点媒体资源应放在 `site/assets/` 的按类型子目录中，并提供有意义的英文小写文件名和 `alt` 文本；公众号配图按 5.3.4 节存放在对应文章组的 `assets/` 中。
6. 公众号文章属于 `content/wechat/` 内容资产，不直接混入 `site/` 发布目录。
7. 公众号凭证只保存在被 Git 忽略的 `.env` 或部署平台的服务端环境变量中；禁止写入 `site/`、文档、测试夹具和日志。

## 4. 路由、导航与搜索

### 4.1 路由规则

- 总览页使用目录默认页：`/`、`/learn/`、`/interview/`。
- 下钻页使用稳定文件名：`learn/concepts.html`、`interview/questions.html`。
- 初学者子模块参数：`concepts.html?topic=<topic>&child=<child>`。
- 面试问题参数：`questions.html?topic=<interviewTopic>&question=<questionId>`。
- 参数值是内容标识符，不是展示文案；不要随中文标题调整而随意改动。
- 页面内切换问题或子模块时，应使用 `history.replaceState` 保留可分享、可刷新恢复的 URL。

### 4.2 顶栏规则

所有五个 HTML 页面都必须保留同一组全局入口：

1. 首页。
2. 初学者总览。
3. 概念下钻。
4. 面试图谱。
5. 题目下钻。

当前页面使用 `aria-current="page"`。顶栏右侧必须保留 `<div data-site-search></div>`，由共享搜索脚本挂载输入框与结果面板。

### 4.3 搜索规则

`site/assets/js/site-search.js` 是唯一的跨页搜索来源。它根据当前页面位于根目录、`learn/` 或 `interview/` 生成相对链接。

- 新增一级主题时，更新 `modules`、`interviewTopic` 和对应内容页的数据源。
- 新增初学者子模块时，更新 `children`，并补齐搜索关键词。
- 搜索结果必须指向存在的本地 HTML 文件，且保留必要的 `topic`、`child` 或 `question` 参数。
- 保持键盘行为：方向键选择、Enter 跳转、Escape 关闭。

## 5. 内容编排规范

本节适用于网站和公众号的所有面向读者内容：标题、正文、图解标签和术语解释使用准确中文，英文专有名词首次出现时说明含义，后文保持同一写法。模型处理文本的小单位统一写作 `token`，首次出现时解释其含义；不要用“词元”替代，也不要把一个 token 等同于一个汉字或英文单词。删除脱离知识点的泛化说明、职责边界模板、空免责声明和没有新信息的过渡句。

### 5.1 初学者内容

网站初学者页的每个一级主题应回答“它解决什么问题、由什么组成、与相邻主题如何配合”。每个子模块应具备：

- 清晰的名称与关键名词解释。
- 图解式结构说明，而不是只罗列定义。
- 独立的“大话”解释，使用具体场景和类比帮助理解，但不复述图解正文。
- 网站保留独立的“机制加餐”栏目，与基础图解和“大话”说明分层呈现；它补充关键机制、取舍或实现边界，不并入“大话”正文。
- 指向对应面试主题的入口。

### 5.2 面试内容

网站面试页的每个主题至少三道题，覆盖：

1. 原理或定义题。
2. 方案取舍题。
3. 生产实践、可靠性或治理题。

每道题必须含有原理、四个可展开的答题点、短记忆点、因果链图解、追问和常见失分点。答案要求能落到输入、决策、执行、验证或升级，不能仅堆叠框架名称。

### 5.3 公众号文章资产

与网站十主题对应的公众号系列按“一级主题总概览 + 子模块下钻”两层组织；独立专题可只设总览组，若有子模块也按相同层级组织。本文所称一组推文，是同一期配套的主文与副文；十主题系列的副文为面试题，独立专题的副文可以是踩坑指南等非面试文章。技术文件名仍沿用 `beginner-main.md` 与 `interview-side.md`，不以文件名限定独立专题的文体。

公众号系列的最终目标是覆盖 2.2 节的全部十个一级主题，但只按用户指令逐个启动、分阶段补齐；未启动的主题不预建文章或清单。另有“项目复盘”等独立专题，不计入十主题的覆盖进度。独立专题仍遵循通用写作、配图、清单、校验和双图文要求；只针对十主题的模块职责、面试题结构和字数上限不套用到独立专题。

案例写作规则适用于新稿和主动精修；既有文章是否完成精修以实际内容为准，不因规范更新而自动改变。不同模块不必套用同一个案例。

对已启动的一级主题，若有 `n` 个子模块，完成该主题交付时必须生成 `n+1` 组推文：

1. `1` 组一级模块总概览；
2. `n` 组子模块下钻，每个子模块各一组；
3. 每组含 `beginner-main.md` 与 `interview-side.md` 两篇文章，因此总计 `2 × (n+1)` 个 Markdown 文件。

#### 5.3.1 文件与元数据

- 十主题系列的 `beginner-main.md` 面向初学者，组合对应主题的基础说明与“大话”内容，可引申机制和工程边界；独立专题主文按 `series.json` 中的 `focus` 写作；
- 每组只维护 `series.json` 登记的正式主文与副文；精修直接更新这两份文章，历史版本通过 Git 提交追溯，不另设对照稿目录或平行文章；
- 推文原稿使用 UTF-8 编码的 Markdown，作为文章的唯一内容源；不要把生成后的 HTML 或 API JSON 当作手工维护的原稿；
- 每个已启动的公众号一级主题或独立专题必须维护一个 `series.json` 模块清单，作为该系列结构的唯一来源。十主题系列省略 `seriesType` 或写 `module`；独立专题必须写 `seriesType: "independent"`。清单统一记录模块标识、总概览与子模块、文章路径、阅读顺序、主文重点、副文边界、写作提纲、提示词文件和配图文件名；面试副文使用 `questionBoundary`，非面试副文使用 `contentBoundary`。生成和校验过程不得再通过解析大型站点 HTML 推断这些信息；
- 新增、删除、改名或调整子模块时，先更新 `series.json`，再生成文章与图片；文章 Front Matter、目录结构和配图引用必须与清单一致；
- 每篇推文原稿必须以 YAML Front Matter 声明 `title`、`author`、`digest`、`cover`、评论开关、`topic`、`content_level`、`submodule` 和 `series_order`；标题不超过 32 个字符，作者不超过 16 个字符，摘要不超过 120 个字符；
- 总概览使用 `content_level: overview`、空 `submodule`、`series_order: 0`；子模块使用 `content_level: submodule`、稳定的英文子模块标识以及对应阅读顺序；
- `title` 必须与正文 H1 一致；`cover` 必须指向本地封面图片；`article_type` 当前使用 `news`；评论开关只使用 `0` 或 `1`；
- 十主题系列正文控制在 3000-5000 个中文字符；独立专题仍不少于 3000 个中文字符，但允许超过 5000 个中文字符。Front Matter 不计入正文长度；所有文章仍必须遵守 5.3.5 节的 HTML 字符与体积上限；

#### 5.3.2 内容结构

- 写正文前必须先在 `series.json` 为每篇文章固定 8-10 个内容段落或一级内容块，并写明每一段解决的问题；没有提纲不得直接生成长文；
- **无上下文成文入口**：先读本节、[面试副文生成规范](./wechat-interview-side-guide.md)、[配图参考规范](./wechat-illustration-reference.md)及目标系列 `series.json`，再把[大语言模型子模块主文](../content/wechat/01-foundation-models-and-inference/submodules/01-llm/beginner-main.md)与[面试副文](../content/wechat/01-foundation-models-and-inference/submodules/01-llm/interview-side.md)作为叙事与分工的质量校准样本。学习其“同一案例逐步推进、主文讲清过程、副文增加可追问的机制与验证、配图承担不同信息任务”；不复制会议案例、十道题、图的形状或未经核实的示意数字。现有文章和自动校验通过均不自动代表质量达标；
- 首稿目标为 3200-3500 个中文字符。写作时按提纲为各段分配字数，首稿直接进入目标区间，避免先写 1500-2000 字短稿再多轮补写；这只是写作起点，不限制独立专题精修后的篇幅。十主题系列终稿仍需符合 3000-5000 个中文字符；
- 若首稿超出目标，不通过删除必要机制、边界或证据强行压缩；若低于目标，只补与当前主题或子模块直接相关的机制、场景、取舍和失败路径，不使用泛化段落凑字数；
- **整篇结构**：主文建议按“具体场景引入 → 概念拆分 → 工作机制 → 工程边界 → 小结”组织；正文开头尽快进入真实问题，不用长篇项目宣言；
- **章节推进**：公众号主文的小标题围绕读者要弄懂的具体问题，可按“输入如何处理 → 机制如何运行 → 能力何时失效 → 工程怎样验证”递进；同级标题尽量保持相近句式。公众号不照搬网站的独立“机制加餐”栏目，而将与主线直接相关的机制说明放在相应环节，不在收束之后补讲原理，造成阅读顺序倒退；
- **主文增量**：写每节前标出“此时案例掌握了什么、这一节新增什么机制或证据、读者因此能判断什么”。小标题可以问问题，但正文应沿同一任务向前推进，不能连续数节只换说法重复“可能出错、需要核对”。删去某节后若读者没有失去新的机制、判断或案例状态，就合并或重写该节；
- **标题承诺与案例范围**：标题若用“多模态模型”“Agent”等宽主题、正文只深入一个输入类型或场景，应在开头说明该场景为何有代表性、本文能讲到哪一层，以及其他输入类型或场景哪些机制不能直接套用；标题不能暗示全面覆盖，正文却只交付单一案例。需要全面介绍时补齐关键分支，不能用一句“其他情况同理”带过；
- **机制落地**：每个核心机制至少说明输入是什么、经过哪项具体变换或计算、哪些信息被保留或损失、怎样影响主案例的可观察结果，以及适用条件。涉及模型架构时，选一至两个经原论文核实的代表性实现说透关键部件和信息流，再说明其他架构的关键差异；仅排列“编码器、投影层、OCR、VLM”等名称，不算解释机制。示意公式和数值必须注明假设，不把一种模型的实现写成所有模型的通则；
- **重复结论清账**：写完主文列出每节最后一个实质判断。若连续两节最终都只得到“仍需核对原图”“不能凭模型猜”等同一结论，应删掉同义段，或给后一节补入独立的故障成因、可执行的核对试验及不同处理结果。同一案例事实可复现，不能靠换标题、图片或比喻把同一判断写成数节；
- **贯穿案例**：一组主文与副文优先共用一个具体、可核对的案例；开头交代原始输入、后来发生的变化、尚缺的信息和读者真正要得到的结果。主案例的事实与约束保持连贯；可以插入短比喻或辅助小场景，但讲完要回到主案例，不用新场景取代主线，也不要求每段机械复述案例；
- **可视输入先展示**：当主文后续反复讨论照片、截图、界面或文档页面中的细节时，在简短交代场景后优先展示读者需要观察的原始对象或教学复现图，再解释相关机制；不要让读者仅凭几段文字想象反光、字段位置或前后差异。图中关键文字、数值、位置、可见与缺失状态须与主副文的事实底稿一致。教学构造图在紧邻图注说明性质，不冒充真实截图、真实票据或模型实测结果；不把这种顺序强加给没有可视输入的文章；
- **同组分工**：两篇文章共用案例事实，不共用成段答案。主文用连续叙述解释现象、成因、失败条件与核对办法；面试副文围绕同一案例组织问题、答题点、追问和判错标准，非面试副文按自身内容边界提供另一种实用视角，均不照抄主文；
- **面试副文增量**：在写题前逐题对照主文，写明新增的计算关系、概念对比、选型依据、验证试验、故障归因或工程条件。仅把主文段落改成问句和四点列表，不算新答案；题目数量由独立机制和篇幅决定，不为凑固定题数把同一结论拆成多题。点击操作、通用安全和隐私等跨模块议题，只有给出本子模块特有的机制与判断时才在子模块副文展开，否则移到总概览或对应主题；独立专题非面试副文继续按其 `contentBoundary` 提供另一视角；
- **主副文并排验收**：正式交付前随机从副文抽三题，逐题在主文中寻找完整答案；若主文已有完整机制、条件与验证，副文就重选或加深该题。反过来检查主文是否把核心机制全部留到副文才讲。两篇应共享事实底稿，不共享段落答案；图片、题目数量和自动校验全达标，也不能替代这一步内容审读；
- 十主题系列的每篇面试副文至少三道题；每道题包含“原理、答题点、记忆点、常见追问、失分点”，题目覆盖定义、方案取舍、可靠性或治理。选题去重、原理深度、固定层级、主副文配图分工、橙色排版和验收方法统一遵循 [公众号面试副文生成规范](./wechat-interview-side-guide.md)。独立专题的非面试副文改按其 `contentBoundary` 和提纲组织，不强制套用题号或上述答题栏目；
- 十主题系列的总概览主文负责解释一级模块在 Agent 体系中的位置、全部子模块的分工、连接关系和共同边界；对子模块机制只做导览，不在总览中抢先完整展开；
- 十主题系列的子模块主文只聚焦一个子模块，讲清工作机制、输入输出、工程实现、典型场景、取舍和失败边界，不再重复总概览的大段定义；
- 十主题系列的总概览面试题聚焦一级模块边界、子模块之间的关系、端到端链路、总体选型和共性治理；子模块面试题聚焦该子模块的具体机制、实现细节、故障处理、评测和实践取舍；
- 同一个例子可以在总览和子模块中出现，但回答的问题必须不同：总览解释跨子模块分工、选择和整体验证；子模块追踪本机制的输入、计算、输出及专项评测。子模块可用一句话说明与工具、权限或发布流程的交接，不展开这些系统级流程；若某段删去子模块名称后仍适用于整个 Agent，应移回总览或改写为本模块特有的问题；
- 同一一级模块内维护题目清单；生成前比对题目标题、核心知识点、答题骨架和追问，写完后并排复核总览与子模块的相近主题。若只是把“全系统”换成某个模型名称，却沿用“查变更 → 拆链路 → 重放 → 回滚”等相同答案骨架，应改写或合并；需要承接的机制知识点在总概览简要点到并链接子模块，具体问题与完整答案留在子模块文章；
- 图解解释关系，正文解释原因和取舍；十主题系列的“大话”使用具体、生活化的表达提供另一种理解角度，不重复图解中的句子，也不另起一条与贯穿案例脱节的事实主线；
- 易混淆的概念应在同一处成对比较，明确各自控制的对象、能解决的问题和不能推出的结论；按阅读媒介选择并列图、短列表或简短代码，不堆多列表格。公众号当前 Markdown 转换器会跳过管道表格行，因此正式推文中的对照内容不能只放在 `| ... |` 表格里；
- 失败示例要按成因拆开，例如旧证据误用、缺失信息被编造、格式不合格、无依据的完成声明；每类写出可观察的错误、核对方法和对应修正，不把不同问题一概归为“幻觉”或“提示词不好”；
- 数字、结构化片段和测试结果用于说明可核对的判断：示意数值明确标为示例，实测结论写清样本、分母与条件；评测至少覆盖普通输入、冲突、缺值和新增信息等与本模块有关的变化，并分开统计不同错误，不用一条漂亮输出或一个总分代替验证；
- 按内容选择一手资料：研究机制查原始或经典论文，协议和标准查正式规范，产品能力与 API 限制查官方文档，工程实现可查源码或一手工程资料。涉及可能变化的字段、限制和版本时，写作前重新核对。

#### 5.3.3 语言风格

- 句子尽量短，用具体对象和动词解释因果关系，少用空泛的抽象名词及“实现……能力”“完成……构建”“进行……处理”等名词化表达；
- 中文先行，英文术语服务于理解：先说明读者能观察到的现象、问题或影响，再引入英文专有名词；不要把英文论文或产品文档逐句直译成中文；
- 标题必须准确说出机制控制的对象和产生的影响。不要为了口语化把技术含义缩窄或改写，例如 temperature、Top-k、Top-p 影响的是候选概率分布、候选范围以及输出的稳定性和多样性，不应笼统写成“改变语气”；
- **单段机制说明**优先采用“现象 → 原因 → 工程影响 → 处理办法”的顺序；这不是整篇文章或章节的另一套提纲。解释 token、上下文、注意力等概念时，避免先堆定义，再补一个脱离上下文的比喻；比喻必须紧接真实机制，并说明它不能覆盖哪些情况；
- 减少模板化和拟人化表达。避免“模型不能读懂”“模型决定关注重点”“这不是……而是……”等绝对化或反复出现的句式，改为描述输入如何被处理、结果为何出现、边界在哪里；
- 写错误与复核时，把判断落到案例里的具体对象、实际核对动作和处理结果，不把几条正确结论拼成连续口号，也不用“免检通行证”“换证据角度”等生硬比喻代替解释。例如两次识别结果相同，应说明它们可能仍依据同一张反光照片，接着写清要回整页核对哪个数字旁的标签，以及看不清时在草稿里如何标记；
- 正文使用 Markdown 建立阅读层级：核心结论、关键边界和容易误解的判断使用 `**加粗**`；参数名、协议对象、字段、数据格式、命令及代码式英文术语使用行内代码，例如 `token`、`Top-p`、`JSON`、`KV Cache`。不要把“加粗”称为“加黑”；
- 加粗和行内代码必须克制。一个自然段通常只突出一个核心判断，不连续加粗整句群，也不把普通英文名词全部包成代码；样式用于帮助扫读，不能替代标题、段落和清楚表达；
- 以问题、场景和判断为主，适当加入轻微幽默，但不写营销口号、鸡汤或夸张承诺；
- 避免机械化开场和收束，例如“本文将带你……”“通过本文你将……”“总的来说”“关键不是……而是……”反复套用；
- 不为了显得专业堆砌框架名称。每个术语都要回答“解决什么问题、怎样工作、有什么边界”。

#### 5.3.4 图片与提示词

- 每篇正文至少引用 5 张本地 PNG/JPG，Front Matter 的 `cover` 不计入这 5 张正文配图；图片放在对应推文组所在目录的 `assets/` 下（总概览放一级模块目录，子模块放各自的子模块目录）；
- 公众号封面由 Front Matter 的 `cover` 单独指定，成片统一为 900×383 PNG，并按公众号实际卡片而非只按本地原图验收。封面必须直接对应文章要讲的机制、案例或判断；关联较弱的标题图、氛围图和通用图标拼贴应删除或重做。禁止在封面出现“一级模块总览”“子模块”“大话系列”“结构图”等项目内部层级名称；
- 主文封面按首条列表大图设计，可以保留精简的主题名与解释性副标题。底部 15%（900×383 时约 58 px）作为微信自动标题遮罩安全区，只放可被遮挡的背景纹理或非必要装饰，不放标题、副标题、关键标签、核心对象、关系线、结论或必须辨认的案例字段。插画应合理使用其余约 85% 的空间，不能为了留安全区又额外留下大块无意义空白；
- 副文封面按右侧小缩略图独立构图，不把主文封面直接缩小、横向裁切或只换颜色。图片中不重复完整文章标题，只保留一个对象、一次比较或一个判断动作形成的强中心视觉；中心组合原则上占画面约 60%，关键信息放进中央正方形安全区。需要比较状态时使用 2—4 个汉字的短标签，并以勾叉、方向、边框或形态配合颜色表达，不能只靠红绿区分。删除左右边缘小卡片、纸堆、装饰面板、横向长链和与判断无关的填充物；
- 主、副封面属于同一组内容时，暖白纸张、低饱和配色、线条质感和字体气质应属于同一视觉家族，但两张图的信息任务和构图必须不同。900×383 画布上的主标题使用 54—62 px 重宋体，推荐 58 px；解释性副标题使用 27—32 px，推荐 30 px；副文短标签使用 30—36 px 粗黑体，推荐 34 px。画布尺寸变化时等比例调整；不再添加低于移动端可读下限的小字；
- 生成式图片优先负责无文字底图，准确中文由 SVG、Canvas 或排版脚本确定性叠加。封面至少检查一次 900×383 原图、一次约 128×128 的居中裁切缩略图，并在真实公众号双图文预览中检查主文标题遮罩和副文中心裁切；只有三处都能辨认主题且无关键信息被挡住，才算通过；
- 正文不要求设置“首图”，也不因排版习惯重复插入封面。只有封面本身同时承担机制、案例或关键关系的解释任务时，才可在正文相应位置复用；
- 正文配图必须承担明确的信息任务，例如解释机制、比较差异、核对证据或展示实验结果。只重复标题、副标题或泛化口号的图片不作为正文配图；案例文章优先画案例中的具体字段、证据与判断，不用可套在任意 Agent 文章上的通用护栏流程代替；
- 正文图内只保留读懂图形所需的对象、标签、数值、箭头和少量直接参与判断的文字；不得在图底另设白条或色条，硬塞“不是实测”“仍须复核”“不能补猜”、论文出处等脱离画面的免责声明或总结句。确有必要的来源、示意性质与适用边界写在紧邻图片的图注或正文，不因移出图片而省略事实核对；
- 新生成或重做的公众号**主文正文图统一使用横版**；面试副文正文图也默认横版，推荐 3:2（如 1536×1024），宽高比均不低于 1.35。副文确需竖图（如长截图或必须连续呈现的纵向步骤）时，应在该组 `prompts.md` 逐张说明信息任务和手机端可读性理由；不能仅因旧图复用、文字卡片堆叠或出图省事而改用竖版。横版须按横向关系重新构图，不得机械拉伸、裁掉内容；两篇均以 330—345 px 手机正文宽度核对关键文字、数值和箭头。封面另按本节封面规则处理。新组在 `series.json` 声明 `beginnerImageAspectMin: 1.35` 与 `interviewImageAspectMin: 1.35`，让校验器逐张检查；副文有已记录的竖图例外时不设置该组副文画幅下限，改为逐张人工验收。历史组按实际重绘进度补齐声明，不因未迁移资产误报全库；
- **每一篇 `beginner-main.md` 至少包含一张原理示意图**，包括一级模块总览主文。原理图必须展示真实机制的关键部件及其依赖、信息流或计算过程；仅有职责分工、业务流程、发布闭环或抽象图标的图片不能充数。总览主文可展示一个横跨子模块的代表性机制，避免重复下钻正文；面试副文可复用已核实的原理图，不强制另画一张；
- 配图先分类：框架图、业务流程图和系统协作图可延续现有的分层、节点、箭头设计；**原理图**先阅读该机制的经典或原始论文及必要的后续资料，找到有代表性的架构图、计算图或对比图，再决定画面结构。不要把任何原理都套进四格流程，也不要只凭生成模型的联想画电路、脑袋或抽象网络；
- 在对应 `prompts.md` 中为每张原理图记录论文名称、可访问链接、具体图号/章节、要解释的机制、必须保留的节点和箭头、简化或改动之处，以及预期图注。优先按论文核对并重新绘制教学图，不直接搬运论文截图或带水印的二手图；需保留原图时先核查授权与署名。正文图注写清“依据/改绘自”的来源，文章末尾附原论文链接；
- 经典论文图的选择、改绘、来源记录和机制核对方法，以及 Transformer、RNN 等具体示例，统一见 [公众号配图参考规范](./wechat-illustration-reference.md)；本规范只保留文章资产必须遵守的原则；
- 先在 `prompts.md` 中写清用途、构图、文字、风格和禁止项，再调用图像模型生成；提示词与最终图片保持一一对应；
- 信息图中的文字优先使用准确中文，英文只保留必要专有名词；文字要少、字号要大、关系线要清楚；
- 生成后逐张检查错别字、漏字、箭头方向、图例含义、尺寸和水印；原理图还要逐项对照论文核查机制、掩码方向、训练/推理阶段和架构版本。图片若反复生成仍有错误，可先用确定性的结构图工具绘制并导出 PNG/JPG，不为凑图片数量使用错误示意图；
- 公众号文章使用不可编辑的 PNG/JPG 成片；SVG 可以作为构图草稿，但不作为最终文章配图。

#### 5.3.5 参考资料与导入限制

- 每篇文章末尾必须有“参考资料”小节，至少提供一个可点击的 HTTP(S) 链接；来源类型按 5.3.2 的资料选择规则确定；
- 封面处理遵循 5.3.4 节。正文开头直接进入案例或问题，不插入只有标题和口号的图片，也不插入“项目入口”“仓库包含总览、初学者图解和面试题”等项目介绍；文章内容已由标题和开场限定范围时，不再用一段导流文重复说明“本篇聚焦什么”；
- 每篇文章只在文末保留一次项目入口，位置放在“参考资料”之后。使用“想看本文在 AI Agent 中的位置，可点击下方 [阅读原文](https://github.com/Jennifer123www/ai-agent-knowledge-map)，从‘当前一级模块’继续阅读”这类简短句式，并让“阅读原文”承担链接，不再同时出现“项目入口”“项目总览仓库”“更多文章见项目仓库”等多种重复叫法；对公众发布前须确认目标读者能访问仓库；若仓库仍不可公开访问，先解决访问问题，不发布只有作者能打开的链接；
- 参考链接必须保留在转换后的 HTML 中，不能只写在项目说明或 Front Matter 里；
- 转换后的正文 HTML 必须少于 20000 个字符且小于 1 MB，不含 JavaScript；正文图片只能引用本地 JPG/PNG，并在创建草稿时先上传微信再替换为微信 URL；
- 精修稿应为新增链接、图注和排版保留 HTML 字符余量，建议转换后不超过 19500 个字符；若接近上限，先精简重复句与过密的行内代码标记，不靠删除必要图片或一手参考资料凑余量；
- 微信导入流程只能创建草稿，不得默认调用发布或群发接口。

#### 5.3.6 校验输出与上下文控制

- `npm run wechat:articles:check` 默认使用简洁模式。失败时只输出失败文件与原因；全部通过时只输出系列数、推文组数和文章数，不打印逐篇统计；
- 校验器按 Front Matter 单独识别封面，并要求每篇另有至少 5 张正文配图；封面即使在正文重复引用，也不计入这 5 张；
- 只有人工排查字数、图片数、参考链接和 HTML 体积时，才运行 `npm run wechat:articles:check:verbose`；不要在每次常规检查中重复输出全部文章明细；
- 校验器只读取已有的 `series.json`，从中获取预期文章、副文边界和图片清单，检查已启动系列的总概览与子模块组是否齐全、每组两篇文章是否配对、`series_order` 是否一致，以及同一系列面试题标题是否重复；独立专题按 `seriesType` 放宽非面试副文形式与中文字符上限，但不放宽 HTML 平台限额。检查通过不代表十个一级主题已经全部覆盖。题目或内容边界是否重合仍须按 5.3.2 节人工复核。不得解析 `site/learn/concepts.html` 等大型页面来重建模块结构；
- 阶段开发先对当前文章运行草稿 dry-run。模块交付前运行一次全系列检查，再读取该模块 `series.json` 的 `groups[].articles.beginner.path` 和 `groups[].articles.interview.path`，以模块目录为基准拼接文章路径。每组执行 `npm run wechat:draft -- --dry-run --theme orange --file <主文路径> --side-file <副文路径>`，一次校验双图文顺序与两篇内容；单篇排查仍使用 `--file`。不带 `--file` 时只检查默认文章，不能代替整组校验。

#### 5.3.7 API 草稿交付与主副文排版

- Markdown、配图、提示词和 `series.json` 是可维护的原始资产。公众号交付通道统一为“Markdown → 带内联样式的 HTML → 上传图片 → `draft/add` 草稿”；不再生成或维护 Word 终稿，也不把导出的 HTML、API JSON 或公众号后台草稿当作第二份内容源。草稿中发现问题，先改原稿或转换器，再重新生成；
- 创建或修改 `series.json` 登记的正式公众号文章 Markdown（`beginner-main.md`、`interview-side.md`）后，先完成该组主副文、配图和本地校验，再在**本轮交付结束前**将对应双图文草稿同步到微信：已有唯一匹配草稿则原位覆盖，没有则新建。只改其中一篇也按整组更新一次；连续编辑同一组时等内容定稿后更新一次，不每保存一段就重复上传。此规则不由 `prompts.md`、项目规范、网站 Markdown 或临时草稿的修改触发，也不自动扩展到未改动的其他组；
- 同一组的正式交付默认是一份**双图文草稿**：`articles[0]` 为 `beginner-main.md` 主文，`articles[1]` 为 `interview-side.md` 副文；独立专题的副文可以不是面试题。两篇的 `topic`、`content_level`、`submodule`、`series_order` 一致。草稿实际顺序由 `--file`、`--side-file` 的传参位置决定；Front Matter 的 `order` 记录并校验预期先后，不负责自动排序。除非用户明确要求单篇，不把两篇拆成互不关联的草稿；
- 正式文章同步草稿默认按[微信接入文档](./wechat-integration.md)使用 `--upsert`。若本轮改过标题，先只读核对唯一旧草稿，再以明确 `media_id` 和原有标题顺序指定原位更新；不把“新标题未匹配”当作“没有旧草稿”。内容、图片、格式或自动校验不通过，缺少 API 凭证，或旧草稿身份不唯一时，不得跳过检查或猜测覆盖对象，应报告未同步原因和待办；
- 两篇共用一套克制的橙色视觉语言。转换器默认使用 `orange` 主题：白色或暖白底、深色正文、橙色章节强调，浅橙色代码区和提示框，灰色居中图注；正式命令仍可显式写 `--theme orange` 便于审计。当前样式以 `lib/wechat/markdown.mjs` 的 `orange` 主题为准；不把第三方编辑器整套模板、复杂嵌套样式或依赖 JavaScript 的效果直接塞进 API 正文；
- 主文是连续讲解，章节标题围绕读者的问题推进；面试副文每题用 `### 原理 / 答题点 / 记忆点` 三级标题，追问和失分点用加粗行内短标签，避免五个三级标题在每题重复造成碎片化；独立专题的非面试副文按自身内容组织清晰层级。两篇沿用相同字体、段距、图片宽度和强调色，不靠换一种配色区分主副文；具体内容分工仍按 5.3.2 节执行；
- 正文保留有节制的 `**加粗**`、行内代码、列表、独立代码块和图注：加粗突出结论或边界，行内代码标参数与字段，代码块使用浅色底与清晰缩进；图注紧跟对应图片，不能并入普通段落。图片顺序、参考资料与文末项目入口按 5.3.4、5.3.5 节保留，不为追求装饰挤占 20000 字符的 HTML 限额；
- 封面处理遵循 5.3.4 节；正文五图仍不计封面；
- 创建前对同组执行 `npm run wechat:draft -- --dry-run --theme orange --file <主文路径> --side-file <副文路径>`，确认两篇标题、作者、摘要、封面、顺序、图片和 HTML 体积；创建后在公众号后台核对双图文卡片、手机端正文、图注、代码块、参考链接及“阅读原文”地址。若平台清理了样式或链接，以后台实际预览为准，修正转换器或后台设置，不仅凭本地 HTML 判断完成；
- 每次真实创建或重新创建草稿前后，按 [微信公众号双图文草稿推送检查规范](./wechat-draft-push-checklist.md) 逐项检查主副文内容、图片、格式、自动校验结果及后台手机预览；任一必检项失败均退回源文件修改，不把全库脚本通过等同于内容验收通过；
- API 只负责创建草稿并返回 `media_id`。最终发布或群发必须另经人工审阅与明确指令；不得把“生成草稿”解释为自动推送给读者。

### 5.4 双版本内容关系

网站与公众号的初学者版和面试版均遵循 5.1、5.2 与 5.3.2 节的分工，不得简单复制正文、图解或语言组织。

## 6. 视觉与交互规范

1. 采用克制的研究型/编辑型视觉：暖白背景、深色正文、绿、青、橙、梅红、蓝作为主题色。
2. 页面是信息导览而非营销落地页：不用大幅渐变、装饰光球、悬浮卡片套卡片或夸张口号。
3. 首页全景图谱必须用可访问的 HTML/SVG 承载中文标签、关键子项和可点击链接；生成式图片只可作为无文字辅助视觉，不能承载中文信息。
4. 图解使用稳定尺寸、清楚的关系线和文字层级；每个点击目标有 `aria-label` 或可读文本。
5. 在窄屏下，绝对定位图谱必须切换为普通网格或纵向流，不能依靠横向滚动阅读主体内容。
6. 按钮、链接与键盘焦点必须可见；搜索结果和切换控件应保持键盘可操作。
7. 使用 `font-size` 的固定或容器适配值，不以视口宽度直接缩放字号；避免负字距。

## 7. 新增或修改内容的同步清单

### 新增一级主题

1. 在 `learn/concepts.html` 中新增初学者主题及子模块数据。
2. 在 `interview/questions.html` 中新增对应面试主题和符合 5.2 节要求的题目。
3. 更新两页之间的映射：`interviewTopicMap` 与 `beginnerTopicMap`。
4. 更新 `site/assets/js/site-search.js` 的 `modules`、`interviewTopic` 和关键词。
5. 更新 `site/index.html` 的全景图谱与主题索引。
6. 更新 `learn/index.html` 与 `interview/index.html` 的总览卡片或主题地图。
7. 为新链接运行站点校验，并手工检查桌面与移动端布局。

### 修改现有主题或子模块

1. 保持既有 `topic`、`child`、`question` 标识符稳定；需要迁移时保留兼容映射或同步修复所有链接。
2. 同时检查首页图谱、初学者总览、概念下钻、面试图谱、题目下钻与搜索结果是否一致。
3. 修改术语时检查两版本与搜索索引的写法一致。
4. 修改页面顶部或页脚元数据时，更新版本、Git 基线/状态和修改时间；不要写入会被下一次提交立即推翻的“当前 SHA”。

## 8. 校验、预览与发布

```sh
# 每次提交前
npm run check
git diff --check

# 修改公众号文章：以下路径只是示例，整组使用主副文双图文 dry-run
npm run wechat:draft -- --dry-run --theme orange --file content/wechat/01-foundation-models-and-inference/submodules/01-llm/beginner-main.md --side-file content/wechat/01-foundation-models-and-inference/submodules/01-llm/interview-side.md

# 修改公众号服务端接入
npm test

# 修改页面：启动预览并手工检查
npm run serve
```

- `npm run check` 必须通过。它检查五个预期页面、共享搜索脚本、本地 HTML 链接、内联脚本语法，以及公众号文章与系列清单。
- 本地预览地址为 `http://127.0.0.1:4173/`。
- 涉及交互、导航、搜索或响应式样式时，至少手工检查：首页、两类总览、两类下钻；搜索命中；桌面和移动端无水平溢出。
- 发布时将 `site/` 作为 GitHub Pages、Netlify、Vercel 或其他静态托管平台的发布目录；不要将仓库根目录误作为站点根目录。
- 公众号回调必须部署到公网 HTTPS 服务；本地回调仅用于测试。接入流程、环境变量和草稿命令见 `docs/wechat-integration.md`。

## 9. Git 与文档维护

- 主分支为 `main`，远程为 `origin`：`git@github.com:Jennifer123www/ai-agent-knowledge-map.git`。
- 提交前校验按第 8 节执行。
- 每个提交保持单一目的；内容、布局、搜索与重构尽量分开提交。

## 10. 完成标准

一次阶段性改动须满足适用范围内的完成标准：

- **共同要求**：面向读者的内容符合第 5 节的通用写作规则。
- **站点页面改动**：页面职责清晰，主题映射符合 2.2 节；导航、搜索、跨版本跳转和 URL 参数正确；桌面与移动端文字不重叠、不溢出，图解可读且可点击。
- **公众号文章改动**：文章与 `series.json` 的路径、顺序和配图一致，正文、图片及参考链接满足 5.3 节要求；交付整组或整个模块时，按 5.3.6 节对每组运行一次主副文双图文 dry-run。
- **公众号 API 草稿**：正式文章 Markdown 创建或修改并通过检查后，同步更新对应双图文草稿；同组主副文顺序、各自封面、橙色主题、图片与链接、后台手机预览符合 5.3.7 节。自动同步只到草稿箱，不发布、不群发。
- **公众号服务端接入改动**：`npm test`、相关草稿 dry-run 和回调验签测试通过；真实凭证与公网回调另行完成联调。
