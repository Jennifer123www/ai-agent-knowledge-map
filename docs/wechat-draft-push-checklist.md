## 1. 适用范围与判定原则

本文用于检查一组 `beginner-main.md` 主文与 `interview-side.md` 副文是否可以创建微信公众号双图文草稿，也用于草稿创建后的后台预览验收。

检查分为四道闸门：内容、图片、格式与平台预览。任一必检项失败，本次结果即为**不通过**，不得用“先推上去再说”代替修正。自动脚本只能证明路径、数量和平台限制等可计算项目通过；事实准确性、图片含义和手机端观感必须人工检查。

这里的“推送”只指调用 `draft/add` 创建草稿，不包含发布或群发。只有用户明确要求导入或重新推送草稿时，才执行真实 API 调用。

## 2. 推送结论

每组文章只能得到以下两种结论：

- **通过，可以创建草稿**：第 3—6 节全部通过，真实推送后继续执行第 7 节；
- **不通过，退回修改**：记录失败项、对应文件和处理办法，修改 Markdown、图片、`series.json` 或转换器后重新从第 3 节检查。

不得以“主要内容没问题”“只有一张图不理想”作为有条件通过。旧草稿不会被新草稿覆盖，返工后需要重新创建草稿并记录新的 `media_id`。

## 3. 组别与文件检查

| 编号 | 检查项 | 通过标准 | 检查方式 |
| --- | --- | --- | --- |
| G-01 | 组别来源 | 主、副文均来自同一 `series.json` 组，不通过解析站点页面临时拼组 | 人工核对清单 |
| G-02 | 文件完整 | 同组同时存在 `beginner-main.md` 与 `interview-side.md`；只有用户明确要求单篇时才例外 | 自动检查 + 人工确认 |
| G-03 | 元数据对应 | 两篇的 `topic`、`content_level`、`submodule`、`series_order` 一致，`order` 分别为主文在前、副文在后 | 自动检查 |
| G-04 | 标题与摘要 | 标题、作者、摘要分别不超过 32、16、120 个字符；正文 H1 与 Front Matter 标题一致 | 自动检查 |
| G-05 | 原稿唯一 | 当前 Markdown 是唯一内容源；没有需要同步的平行稿、导出 HTML 或 Word 版本 | 人工确认 |

## 4. 内容检查

### 4.1 两篇共同检查

- [ ] 主题范围与 `series.json` 中的 `focus`、`outline`、`questionBoundary` 或 `contentBoundary` 一致，没有写到相邻子模块的主体内容。
- [ ] 主、副文使用同一组可核对的案例事实；人物、时间、状态、输入、缺失信息和处理结果没有互相矛盾。
- [ ] 核心术语、数字、公式、接口字段和技术结论已核对；研究机制有经典或原始论文，协议与产品限制有官方资料。
- [ ] 示例数字明确标注为示意；声称来自测试的结果写明样本、条件和分母。
- [ ] 正文开头直接进入问题或案例，没有“项目入口”“本文将带你”等模板化导语，也没有只重复标题的正文首图。
- [ ] 每篇末尾有“参考资料”，至少包含一个 HTTP(S) 链接；之后只保留一次“阅读原文”入口。
- [ ] 十主题系列正文各为 3000—5000 个中文字符；独立专题不少于 3000 个中文字符，并仍满足 HTML 限额。
- [ ] 表达自然、具体，没有生硬直译、连续口号、空泛职责说明或为凑字数加入的泛化段落。

### 4.2 主文检查

- [ ] 主文以连续叙述解释现象、机制、工程影响、失败条件和核对办法，不写成题库或卡片堆叠。
- [ ] 总概览讲模块位置、子模块关系和共同边界，不抢先完整展开各子模块；子模块文章只聚焦本模块的输入、过程、输出、取舍和专项失败。
- [ ] 至少有一处真正的原理说明，交代关键部件、信息流或计算关系及成立条件，而不是只给比喻和结论。
- [ ] 章节顺序符合读者理解过程，相关机制放在首次需要它的位置，不在文章收束后重新补讲主原理。

### 4.3 副文检查

- [ ] 副文可以独立阅读，不依赖“如主文所述”“见上一篇”补全关键答案。
- [ ] 副文没有把主文改成问答形式后逐段复述；同一知识点应增加答题边界、对比、验证、排错或工程取舍。
- [ ] 十主题面试副文至少三道题，题目覆盖原理或定义、方案取舍、生产实践或可靠性治理。
- [ ] 每道题包含“原理、答题点、记忆点、常见追问、失分点”；原理有知识增量，答题点可展开，追问能区分理解深浅，失分点可以明确判定。
- [ ] “记忆点”是独立三级标题，下方紧跟浅橙引用框；引用框内不重复“记忆点：”，也不借记忆点引入新的技术结论。
- [ ] 与同一级模块的总览及兄弟副文比较过题目标题、答案骨架和追问，没有仅替换名词的重复题。

## 5. 图片检查

### 5.1 数量、路径与分工

- [ ] 主文和副文各自至少引用 5 张正文 PNG/JPG；`cover` 不计入正文图片数量。
- [ ] 图片均位于本组 `assets/` 目录并被 `series.json`、Markdown 和文件系统一致引用，没有失效路径或未登记图片。
- [ ] 主文至少有一张原理图；原理图展示关键部件、依赖、信息流或计算过程，不能用通用四格流程冒充。
- [ ] 主文图片优先解释机制、过程和案例；副文图片优先承担对比、诊断、证据审计、方案选择或评测判据。
- [ ] 主、副文没有整套复用图片；默认只共享 1—3 张必要原理图，副文正文图复用比例原则上不超过 40%。

### 5.2 单图有效性

每张图逐一回答以下问题；任一问题答“否”，该图需要修改或删除：

1. 这张图能否用一句话说清它在正文中解释的具体问题？
2. 图中是否提供了正文之外的结构、关系、差异或证据，而不只是把段落装进方框？
3. 图前文字是否提出了读图问题，图后文字是否解释了读者应得到的判断？
4. 图中的中文、英文术语、数字、公式、箭头、图例和流程方向是否正确？
5. 原理图是否能追溯到论文或官方资料，并在 `prompts.md` 和图注中记录依据或改绘来源？
6. 图片是否没有水印、错别字、乱码、含义不明的装饰元素和与主题无关的机器人、盾牌等图标？

### 5.3 视觉一致性与封面

- [ ] 正文图使用暖白底、深灰文字和低饱和浅色块；高饱和色只用于少量箭头、短标签或警告。
- [ ] 图片标题不过大，原则上不超过画布高度的 8%—10%；没有贯穿左侧的装饰竖线、大面积实色标题条、渐变、霓虹和立体阴影。
- [ ] 连续查看同一篇全部图片时，标题尺度、边距、线条、色彩强度和信息密度协调，没有某一张突然过亮、过空或过吵。
- [ ] 主、副文分别使用与正文强相关的封面；正文不保留只承担标题展示或氛围装饰的首图。
- [ ] 主文封面按列表大图检查，底部约 25% 的微信标题遮罩安全区没有关键内容。
- [ ] 副文封面按右侧小缩略图独立设计：不重复完整文章标题，只保留一个约占画面 60% 的强中心视觉和必要短标签；关键内容位于中央正方形安全区，裁切后仍能辨认，颜色不是状态的唯一区分方式。

## 6. 格式与自动校验

### 6.1 Markdown 与渲染格式

- [ ] 两篇都使用橙色主题：白色或暖白底、深色正文、橙色章节标题、浅橙提示或代码区域、灰色居中图注。
- [ ] 主文章节层级连续，不以加粗段落代替标题；副文使用 `## 问题 n` 和 `### 原理 / 答题点 / 记忆点`。
- [ ] 核心结论才使用加粗，参数、字段、协议对象和代码式术语才使用行内代码；没有整段加粗或每句都套样式。
- [ ] 独立代码块保留缩进和浅色底；图注紧跟图片，不混入普通正文。
- [ ] 对照信息没有只写在 Markdown 管道表格中，以免转换后丢失。
- [ ] 转换结果不含 JavaScript，HTML 少于 20000 个字符且小于 1 MB；精修目标不超过 19500 个字符。
- [ ] 所有正文图片均会先上传微信并替换为微信 URL；本地图片单张符合微信上传限制，或由现有脚本完成临时压缩。

### 6.2 推送前必须执行的命令

```sh
npm run wechat:articles:check
npm run wechat:draft -- --dry-run --theme orange --file <主文路径> --side-file <副文路径>
npm run check
npm test
git diff --check
```

命令结果按下列标准判定：

- 任一命令退出码非零即不通过；
- `dry-run` 必须显示 `articleCount: 2`，主文排第一、副文排第二；
- 两篇的封面路径、正文图片清单、标题、作者、摘要和 `contentSourceUrl` 必须与预期一致；
- `htmlCharacters` 必须小于 20000，建议不超过 19500；接近上限时先清除重复表达和过密样式，不删除必要原理、图片或一手资料；
- 全库校验通过不代表人工内容与图片检查通过，第 4、5 节仍须逐项完成。

## 7. 创建草稿后的后台检查

取得 `media_id` 后，不直接宣布文章可发布。必须在公众号后台和手机端预览完成以下检查：

- [ ] 双图文卡片只有一组，主文在前、副文在后，标题和摘要没有截断出歧义。
- [ ] 主文大图底部标题遮罩未覆盖关键内容；副文小缩略图的中心视觉、短标签和状态符号清楚，中央安全区没有被裁坏，也没有重复完整文章标题。
- [ ] 两篇的橙色主题一致；标题层级、段距、列表、引用框、行内代码和代码块没有被微信清理到影响阅读。
- [ ] 副文每个“记忆点”均显示为橙色独立标题和浅橙引用框，引用框内不重复栏目名。
- [ ] 正文图片按预期顺序完整显示，清晰度可接受，图注没有错位，图片前后语义连续。
- [ ] 参考资料仍可识别；正文外链若被平台限制，应确认“阅读原文”能够正确跳转到 `content_source_url`。
- [ ] 手机端无横向溢出、超小文字、过长代码行、异常大空白或段落黏连。
- [ ] 抽查关键事实、数字和案例状态，确认上传内容与最后一次本地审阅版本一致。

后台预览失败时，先修改 Markdown、原图、Front Matter 或转换器，再重新执行 dry-run 和真实草稿创建。不要只在公众号后台临时改出一个无法回写项目的版本。

## 8. 检查记录模板

每次真实创建草稿后，至少记录以下信息，便于识别新旧草稿：

```text
文章组：<series/group id>
主文：<title>
副文：<title>
本地提交：<git sha；若尚未提交则写 dirty>
dry-run：通过 / 不通过
内容检查：通过 / 不通过
图片检查：通过 / 不通过
格式检查：通过 / 不通过
草稿 media_id：<id>
创建时间：<YYYY-MM-DD HH:mm CST>
后台与手机预览：通过 / 待检查 / 不通过
失败项与处理：<没有则写无>
旧草稿处理：保留 / 已人工删除
```

只有“内容、图片、格式、dry-run、后台与手机预览”全部通过，才可以把该草稿标记为**待发布终稿**。发布或群发仍需用户另行明确授权。
