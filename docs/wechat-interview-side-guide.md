## 1. 适用范围

本文适用于十主题公众号系列中的 `interview-side.md`。它是 [项目规范](./project-specification.md) 5.3 节的执行细则；独立专题的踩坑指南等非面试副文不强制套用题号和答题栏目。

面试副文不是主文的缩写版，也不是题库清单。它应让读者既能回答“原理是什么”，也能继续回答“为什么会出现这个现象、怎样验证、怎样排错、有哪些取舍”。

## 2. 生成前先确定边界

1. 从所在系列的 `series.json` 读取 `focus`、`outline` 和 `questionBoundary`，不得通过重新解析网站 HTML 推断题目。
2. 在 `series.json` 中先固定 8—10 个内容块和每块解决的问题，并为首稿分配字数；首稿目标为 3200—3500 个中文字符，不先生成短稿再用空话补齐。
3. 题目至少覆盖三类：原理或定义、方案取舍、生产实践或可靠性治理；每篇至少三道题，具体数量由知识边界、3000—5000 个中文字符和 20000 字符 HTML 限额共同决定。
4. 总概览副文聚焦跨子模块关系、整体选型、端到端验证和共性治理；子模块副文聚焦该机制的计算过程、实现细节、专项故障和专项评测。
5. 同一一级模块内，比对所有副文的题目标题、核心知识点、回答骨架和追问。只更换模块名称、答案仍相同的题目视为重复，应改写、合并或移到总概览。
6. 为每道题写一句“这道题要证明什么”。无法写出独立判断目标的题，不进入正文。
7. 将主文和拟写副文并排做题目表：`题目｜主文已解释的内容｜副文新增的机制或判断｜怎样验证或追问｜预定图型`。第三列若只写“换成答题点”“再强调复核”，这道题尚无知识增量，应合并或重选。表只用于写作规划，不直接作为公众号 Markdown 管道表格发表。
8. 主案例先列一份事实底稿：原始输入、后来的变更、仍未知的字段、允许与禁止的动作、可引用的证据。逐题引用同一底稿；允许更换短比喻，不允许悄悄增加案例事实。没有对话上下文时，可对照[大语言模型子模块面试副文](../content/wechat/01-foundation-models-and-inference/submodules/01-llm/interview-side.md)学习题目推进和回答密度，但不得复制其十题清单或会议案例。

## 3. 主文与副文怎样配合

- 两篇共用案例事实、术语口径和资料来源，避免同一场会议在两篇中出现不同时间、地点或状态。
- 主文负责连续解释现象、机制、过程和失败边界；副文负责把这些知识转成可作答、可追问、可验证的判断。
- 副文可以复用主文已经核实的核心原理图，但不能连续复制主文段落、案例叙述和图片顺序。
- 同一个知识点若在主文回答“它怎样工作”，副文应进一步回答“怎样向面试官解释、如何区分相似概念、怎样证明方案有效”。
- 副文必须独立可读，不能用“如主文所述”“先看上一篇”代替必要解释。
- 同一案例的事实可以重复，结论不应原样重复。每道题至少提供一项主文没有展开的机制、条件、对照、实验设计或错误归因；如果删去副文答案后，读者仍能从主文逐段拼出完整答法，就需要重写。
- 子模块副文先守住子模块特有的问题。涉及 Agent 点击、提示注入、权限、隐私等跨模块题时，要说明该题为何必须由此子模块回答；只需通用流程就能作答的，移到总概览或对应模块，不以扩大范围填满题数。
- 选题要从主文已讲到但尚未展开的**技术分叉**继续走，而非再问一次主文的结论。例如多模态主文讲“缩图会丢小字”，副文可计算固定图块下分辨率与块数的取舍；主文讲“局部图要映回原图”，副文可说明坐标变换及旋转例外；主文讲“年份未知”，副文可讨论分数校准为何不能补足缺失事实。这些只是增量示例，不是其他子模块必须照抄的题单。
- 题目表的新增列必须写出**可追问的硬内容**：公式的假设、两种架构的差别、能区分两类故障的实验、阈值的标注口径或失败时的处理分支。若只能写“加强复核”“注意风险”“回到原图”，即使主文没有这句话，也不算足够的新知识。

## 4. 每道题的固定结构

使用下列 Markdown 层级；`常见追问`和`失分点`是行内加粗短标签，不另设三级标题：

```markdown
## 问题 1：准确、可追问的问题标题

### 原理

解释真实机制、因果关系和成立条件。

### 答题点

给出三至四个能够继续展开的要点。

### 记忆点

> 一句帮助回忆顺序的话。

**常见追问：** 面试官可能怎样继续追问，以及回答边界。

**失分点：** 一个或两个具体误区。
```

各栏目的职责如下：

- **原理**：回答关键部件是什么、信息怎样流动、前一步怎样影响后一步、哪些条件成立时结论才有效；不能只有一句定义。
- **答题点**：通常按“机制说明 → 案例影响 → 验证方法 → 工程取舍”展开。三至四点应互相独立，不把同一句话换种说法重复三次。
- **记忆点**：使用独立的橙色三级标题，下一行放浅橙底、左侧细橙线的引用框；引用框中只写帮助回忆顺序的正文，不再重复“记忆点：”标签。它不承担新的技术结论，不能替代原理和答题点。
- **常见追问**：选择真正能检验理解的追问，如相似概念区别、参数变化、失败条件或验证办法；同时给出回答边界。
- **失分点**：指出具体错误说法，例如“低温度必然更准确”“合法 JSON 等于事实正确”，不用“回答不完整”“理解不到位”等空泛评语。

答题点可写成紧凑的三至四项短列表，也可写成能依次展开的短段落；不为形式整齐把每题硬拆成四条。每题只保留“原理、答题点、记忆点”三个三级标题；十题反复使用五个三级标题，会把一篇文章切成五十块，削弱连读节奏。

## 5. 原理深度与知识增量

1. 原理不能因篇幅限制被压成口号。至少交代机制对象、关键步骤或计算关系、成立条件以及它对当前案例的影响。
2. 丰富内容应增加知识，不做同义扩写。可补充必要的公式含义、训练与推理差异、状态边界、缓存命中条件、错误分类或评测口径。
3. 公式只在能解释现象时出现，公式后说明每一项控制什么；不为显得专业堆数学符号。
4. 对易混概念成对解释。例如：窗口容量不等于信息利用，输出稳定不等于事实正确，格式合法不等于取值可信，`KV Cache` 不等于结果缓存。
5. 失败原因必须拆开。旧证据误用、缺失事实编造、无执行回执却声称完成、结构与正文矛盾，应分别写核对方法和修正路径。
6. 研究机制优先查原始或经典论文；规范、协议和产品行为优先查官方资料。正文末尾保留链接，原理图写明依据或改绘来源。
7. 中文表达以自然、准确为先；英文专有名词首次出现时解释。`token` 等约定保留英文原词，不生硬套用少见直译。

## 6. 面试副文配图

1. 封面与正文图分开计算；副文正文至少五张图，封面不计入。
2. 主文与副文共用事实口径和视觉系统，不共用整套图片。默认共享一至三张必要的核心原理图，副文正文图复用比例原则上不超过 40%。
3. 主文图优先解释机制、过程和案例；副文图优先承担对比、诊断、证据审计、方案选择和评测判据。
4. 一张图只回答一个问题，并提供正文之外的关系信息。只把段落重排成方框、重复标题或放置氛围插画，不算有效配图。
5. 涉及底层原理时，先阅读经典论文或官方技术资料，确定代表性架构图、计算图或对比图，再改绘中文教学图。不得凭生成模型联想发明机制。
6. 正文图采用暖白底、深灰文字和低饱和浅色块；高饱和颜色只用于细边、箭头、短标签和关键警告。主标题原则上不超过画布高度的 8%—10%。
7. 禁止贯穿整张图左侧的装饰竖线、大面积实色标题条、多个高饱和色块、渐变、霓虹、立体阴影、PPT 母版、机器人和盾牌图标。
8. 同一篇副文的图片标题尺度、边距和颜色强度保持一致。生成后把图片连续排开检查，避免单张合格、连读时却过于喧闹。
9. 图片生成后逐字检查中文、英文术语、数字、公式、箭头和图例；示意数字必须注明是示意，不伪装成实测结果。
10. 新生成或重做的副文正文图默认横版，推荐 3:2、宽高比不低于 1.35；确需竖图时在本组 `prompts.md` 逐张说明它为何比横图更适合当前问题，并在手机宽度下检查。画幅约束和清单声明遵循[项目规范 5.3.4 节](./project-specification.md)。
11. 技术对照图要给出副文特有的可追问内容：明确比较条件、关键变量、计算或排障步骤和结论边界。能用同一输入的单变量对照区分故障时，不另画一张只换标题的主文流程图；涉及参数量、概率或指标时写清计算单位与分母，教学数值不冒充实测。具体画法与核对见[公众号配图参考规范 7.6 节](./wechat-illustration-reference.md)。

完整的图型选择、提示词结构和验收规则见 [公众号配图参考规范](./wechat-illustration-reference.md)。

## 7. 排版与平台限制

- 副文使用橙色主题：白色或暖白正文底、深色正文、橙色章节强调、浅橙代码和提示区域、灰色居中图注。转换器默认主题为 `orange`。
- 一级题目使用 `## 问题 n`，题内的“原理”“答题点”和“记忆点”使用 `###`；“记忆点”标题下紧跟引用块，引用块内不重复栏目名；常见追问与失分点使用加粗短标签。不能为了节省 HTML 把全部层级退化为连续加粗段落。
- 参数、字段、协议对象和代码式术语使用行内代码；自然语言结论使用加粗。二者都应克制，不能每句都加样式。
- 正文控制在 3000—5000 个中文字符。转换后的 HTML 必须少于 20000 个字符，精修目标不超过 19500 个字符。
- 接近 HTML 上限时，先删除重复句、重复题目和过密的行内代码，不删除必要原理、配图或一手参考资料，也不取消题内层级。
- 正文末尾保留“参考资料”和一次“阅读原文”入口；开头不放项目介绍、仓库说明或仅有标题的首图。

## 8. 完成前检查

按以下顺序验收：

1. **边界检查**：与总概览、副文兄弟模块及主文没有换标题重复。
2. **原理检查**：每道题包含真实机制、成立条件、案例影响和验证办法，没有只做同义扩写。
3. **答案检查**：答题点可展开，记忆点不代替答案，追问能区分是否真正理解，失分点具体可判。
4. **图片检查**：正文至少五张；共享图比例符合要求；无装饰竖线；标题不过大；色彩克制；中文、数字、箭头正确。
5. **排版检查**：题号、原理与答题点三级标题、独立“记忆点”标题及其浅橙引用框、追问和失分点层级完整；橙色主题生效。
6. **增量与节奏检查**：逐题回看题目表的“副文新增”列；不能只把主文改成四点列表；连续三题若都得出同一句“仍需核对”，必须补上不同机制或合并。检查是否把通用跨模块题误放进子模块，以及是否把追问、失分点错误地升为三级标题。
7. **平台检查**：标题、作者、摘要、正文字符、HTML 字符、图片路径和参考链接均通过校验。
8. **双图文检查**：主文在前、副文在后，各用自己的封面，案例事实一致，副文可独立阅读。
9. **内容回归抽查**：从副文抽三题，在主文里寻找完整答案；找到即重选或深化。再从主文抽三个核心机制，确认没有留给副文才首次解释。读者即使不看图片，也应能说出关键变换、信息损失和失败条件。

建议命令：

```sh
npm run wechat:articles:check
npm run wechat:draft -- --dry-run --theme orange --file <主文路径> --side-file <副文路径>
npm run check
npm test
git diff --check
```

公众号后台或手机端预览仍是最终排版依据。若平台清理样式或裁切封面，应修正 Markdown、转换器或封面本身，再重新创建草稿。
